# インシデントレポート: イメージ取得用トークンの期限切れによる、デプロイ時の本番停止

**発生日**: 2026-11-14 23:58 頃 〜 2026-11-15 00:10 頃（JST。以下、時刻は JST）
**対象**: chumon-hub（K3s / `ghcr.io/fumiakic/chumon-hub:latest`）
**影響**: **サービス全断**（`replicas: 1`）。約 12 分。利用者への影響なし（深夜で利用が無かった。owner の確認）。データ損失なし（本アプリは現時点でステートレス）
**検知**: GitHub Actions `deploy.yml` の `kubectl rollout status --timeout=180s` がタイムアウトで失敗
**復旧**: `ghcr-secret` を新しいトークンで作り直し、ImagePullBackOff の Pod を削除して作り直させた
**重大度**: 中（本番が停止し、手動の介入を要した。利用者への影響は無かった）

## 2. 直接原因

**ノードが GHCR からイメージを取得するための認証情報（`ghcr-secret`）のトークンが、2026-11-10 に期限切れになっていた。**

GHCR のパッケージは非公開なので、取得には認証が要る。期限の切れたトークンでは、GHCR のトークン発行の段階で 403 になり、イメージの取得に進めない。新しいイメージそのものには問題が無かった（復旧後、同じイメージで起動している）。

---

## 3. 根本原因（設計と判断）

### 3.1 期限のある認証情報を、期限を追わずに置いていた（2 回目）

同じ Secret の期限切れは、2026-08-12 に続いて 2 回目である。1 回目は、経緯として記録したが、期限を追う仕組みも、切れたときに停止に至らないようにする仕組みも入れなかった。

### 3.2 デプロイが、新しいイメージを取得できることを確かめる前に、旧 Pod を止める

Deployment は `maxSurge: 0` / `maxUnavailable: 1` で、旧 Pod を止めてから新 Pod を起動する。これはノードのメモリの予算を守るための設定で（[`../ops/k3s-node-config.md`](../ops/k3s-node-config.md)）、単一ノード・`replicas: 1` の構成では外せない。

その結果、**新 Pod が起動できない原因が何であっても、デプロイは本番の停止になる。** 認証情報の期限切れは、その原因の 1 つにすぎない。レジストリの障害や、ネットワークの不通でも、同じことが起きる。

2026-08-20 のインシデント（[`2026-08-20-next-16.3.1-standalone.md`](2026-08-20-next-16.3.1-standalone.md)）では、新 Pod が起動に失敗しても旧 Pod が稼働を続け、停止は起きなかった。当時は既定の RollingUpdate で、新 Pod を先に起動していたためである。#347（2026-09-19）で `maxSurge: 0` にした時点で、この保護は無くなっていた。同文書の §6.5 が挙げる「RollingUpdate が旧 Pod を守った」は、今の構成には当てはまらない。

### 3.3 `imagePullPolicy: Always` では、コンテナを起動するたびにレジストリの認証が要る

Kubernetes の公式文書によると、`Always` では、kubelet がコンテナを起動するたびに、コンテナランタイムがレジストリに問い合わせて、タグを digest に解決する。レイヤーがノードに残っていても、問い合わせは行う。

したがって、トークンが切れていた 11-10 から 11-14 までの間は、デプロイをしなくても、コンテナの再起動（liveness probe の失敗、ノードの再起動など）が 1 回起きれば、本番は停止していた。今回は、デプロイがたまたま最初の引き金になった。

### 3.4 デプロイの間隔が空いて、期限切れが表に出なかった

10-19 から 11-14 まで、main に本番へ出る変更が無かった。認証情報が有効かどうかを確かめる機会は、デプロイのときにしか無い。

## 5. 良かった点（維持すべき運用）

- **失敗が明示的にエラーになった。** `rollout status --timeout=180s` が run を失敗させたので、デプロイの直後に気付けた。
- **原因の特定が早かった。** kubelet のイベントが、失敗した段階（トークンの発行）と HTTP ステータスを示していた。
- **デプロイの前に本番を照合し、復旧点の digest を控えていた。**
- **新しいトークンを Secret に入れる前に、同じ URL で通ることを確かめた。** トークンの値は、画面にもシェルの履歴にも残していない。

## 6. 再発防止策

### 6.1 採用: 旧 Pod を止める前に、新しいイメージを取得できることを確かめる（owner 判断 / 2026-11-15）

`deploy.yml` で、`kubectl rollout restart` の前に、ノードが新しいイメージを取得できることを確かめる。取得できなければ、デプロイを失敗させ、旧 Pod は止めない。別の fix の PR で行う。2026-11-26 追記: #408（2026-11-15 にマージ）で実装した。`deploy.yml` の deploy ジョブが、restart の前に、使い捨ての Pod で新しいイメージを取得できることを確かめる。仕組みは [`../ops/branch-and-deploy.md`](../ops/branch-and-deploy.md) §2.1。

これは §3.2 への対策で、認証情報の期限切れに限らず、イメージを取得できない原因の全般に効く。期限切れは、本番の停止ではなく、デプロイの失敗として表に出るようになる。

### 6.2 採らない（owner 判断 / 2026-11-15）

- **運用での期限の管理**（期限を控え、切れる前に更新する予定を入れる）を、対策としては採らない。
- **期限の無い認証への切り替え**は採らない。検討時の評価は、「漏れたときの影響が大きくなる」「Cloud Run への移行（ADR-1）で、この Secret 自体が不要になる」だった。

### 6.3 残るリスク

- **6.1 は、デプロイを伴わないコンテナの再起動には効かない。** §3.3 のとおり、トークンが切れた後にコンテナが再起動すると、デプロイをしなくても本番は停止する。新しいトークンの期限は **2027-02-13** である。その日までに k3s の撤去（移行エポック）が終わっていなければ、期限の前にトークンを更新する必要がある。
- **6.1 は、取得できたイメージが起動に失敗する場合には効かない。** §3.2 のとおり、今の構成では、起動に失敗するイメージ（2026-08-20 の種類）のデプロイも本番の停止になる。これを防いでいるのは、CI の起動スモークだけである。
- **切り戻しの手順は、イメージの取得の認証が通ることを前提にしている。** ADR-6 の受け入れ条件 7（切り戻しの手順）を定めるときに、この前提を明記する。 2026-11-16 追記: #399 の本文の「切り戻しの手順（条件 7）」の前提に明記した。

## 8. 一言でまとめると

**壊れていたのは新しいイメージではなく、それを取りに行くための鍵だった。** 鍵は 4 日前に切れていたが、デプロイもコンテナの再起動も無かったので、誰も気付かなかった。そして今の構成では、旧 Pod を先に止めるので、新しい Pod が起動できない理由が何であっても、デプロイは本番の停止になる。

同じ鍵の期限切れは 2 回目である。1 回目に記録だけで済ませたことが、2 回目を停止にした。
