# インシデントレポート: Next.js 16.3.1 へのアップデートによる本番デプロイ失敗

**発生日**: 2026-08-20
**対象**: chumon-hub（K3s / ghcr.io/fumiakic/chumon-hub:latest）
**影響**: **ユーザー影響なし**（旧 Pod が稼働継続。ダウンタイム 0、データ損失なし）
**検知**: GitHub Actions `deploy.yml` の `kubectl rollout status --timeout=180s` がタイムアウトで失敗
**復旧**: PR #288（`d8cc4ca` の revert）マージ後、新 Pod が 1/1 Running を確認
**重大度**: 低（可用性は維持されたが、デプロイパイプラインが停止した）

---

## 1. 何が起きたか（タイムライン）

| 時点 | 出来事 |
|---|---|
| — | Dependabot が `next 16.2.11 → 16.3.1` を PR #284 として提案 |
| — | Vercel の失敗チェックが混入（別件）→ 調査の結果 v0 由来の残骸と判明、PR #287 で除去 |
| — | PR #284 をマージ（`d8cc4ca`）。**CI は全て green** |
| — | `deploy.yml` 起動 → イメージビルド・GHCR push 成功 → `kubectl rollout restart` 実行 |
| — | `rollout status` が `1 old replicas are pending termination...` で停止、180 秒でタイムアウト |
| — | 原因を特定。ローカルで A/B 再現し、16.3.1 の standalone 出力の不具合と確定 |
| — | PR #288 で revert → マージ → 新 Pod 1/1 Running、復旧完了 |

---

## 2. 直接原因（技術的な根本原因）

**Next.js 16.3.1 の `output: 'standalone'` 出力に、`@swc/helpers` の `esm/` ディレクトリが含まれない。**

`server.js` 起動時に以下で即クラッシュする:

```
Error: Cannot find module
  '.../@swc/helpers/esm/_interop_require_default.js'
code: 'MODULE_NOT_FOUND'
```

### A/B 検証結果（クリーン環境で実測）

| next | `next build` | standalone 出力の `@swc/helpers` | `node server.js` | `/` の応答 |
|---|---|---|---|---|
| 16.2.11 | 成功 | `cjs/` + `package.json` | ✅ Ready | **200** |
| 16.3.1 | 成功 | `cjs/` + `package.json`（**`esm/` 欠落**） | ❌ 即クラッシュ | 応答なし |

16.2.11 の standalone にも `esm/` は含まれていなかったが、そちらは ESM 側を要求しないため問題にならなかった。**16.3 系で参照側の解決経路が変わったことによる upstream の回帰**であり、こちらの設定ミスではない。

補足: この事象は libc 非依存（glibc 環境でも同一に再現）のため、ADR-4（musl/Alpine の非対称）の再検討トリガには該当しない。

### なぜ K3s が「1 old replicas are pending termination」で止まったか

```
replicas: 1
strategy: RollingUpdate（既定）
  maxSurge:       25% → 切り上げ 1
  maxUnavailable: 25% → 切り捨て 0   ← ここが効いた
```

`maxUnavailable: 0` のため、**新 Pod が Ready になるまで旧 Pod を終了できない**。新 Pod は起動即クラッシュ → CrashLoopBackOff → readinessProbe 失敗 → 旧 Pod が終了待ちのまま 180 秒でタイムアウト。

**この挙動は設計どおりで、実は今回の「守り」として機能した。** 旧 Pod がサービスを継続したためユーザー影響がゼロに抑えられている。

## 3. 検知が遅れた真因（プロセスの穴）

技術的原因は upstream にあるが、**本番に到達させてしまった責任はこちら側の検証設計にある。**

```
next build 成功 → docker build 成功 → CI green → 本番で起動失敗
                                        ↑
                              ここで止められるはずだった
```

`ci.yml` の `build-check` は `docker/build-push-action` で `push: false` のビルドのみを行っており、**「ビルドできる」ことしか検証していない。「起動する」「ヘルスチェックが通る」は未検証**だった。今回の回帰は「ビルドは通るが実行時に落ちる」クラスであり、この穴を正確に通り抜けた。

---

## 4. なぜ今まで起きず、今回初めて気付いたのか

3 つの要因が重なった。

### 要因 1: Next.js のマイナー更新はそもそも稀

`next` のバージョン遷移を全履歴から追うと:

```
16.0.3 → 16.0.7 → 16.1.1 → 16.1.5 → 16.1.6 → 16.1.7
       → 16.2.3 → 16.2.4 → 16.2.6 → 16.2.9 → 16.2.10 → 16.2.11
       → 16.3.1（今回）
```

マイナー更新（16.1→16.2、16.2→16.3）は **4 か月に 1 回程度**しか発生しない。パッチ更新（16.2.10→16.2.11 等）は `dependabot-auto-merge.yml` で `semver-patch` のみ自動マージされ、standalone のファイルトレースを壊すような変更をまず含まない。**壊れうる種類の更新の頻度が、そもそも低い。**

### 要因 2: この不具合は 16.3 系で初めて生まれた

`esm/` 欠落と参照側のミスマッチは Next.js 16.3.0/16.3.1 の回帰である。過去のバージョンには存在しなかったため、遭遇のしようがなかった。

### 要因 3（最も重要）: 検知機構が入ったのが前回のマイナー更新の「後」だった

| 日付 | 出来事 |
|---|---|
| 2026-04-11 | **前回のマイナー更新** `16.1.7 → 16.2.3`（#107） |
| 2026-05-17 | `deploy.yml` に **`kubectl rollout status --timeout=180s` を追加**（#157） |
| 2026-07-20 | `ci.yml` に lint/typecheck/format ゲートを追加（#240） |
| 2026-08-20 | **今回のマイナー更新** `16.2.11 → 16.3.1`（#284） |

つまり **#157 で失敗検知を入れて以降、Next.js のマイナー更新は今回が初めて**だった。

そして #157 以前の `deploy.yml` は `kubectl rollout restart` を実行するだけで終了していた。この構成では、**新 Pod が CrashLoopBackOff に陥っていても GitHub Actions は green で完了する**。旧 Pod がサービスを継続するため画面上も正常に見える。

> つまり「今まで起きなかった」というより、**「今までは起きても気付けない構造だった」**可能性がある。今回は #157 で入れた検知機構が、意図どおり初仕事をしたと評価できる。

## 5. 非エンジニアがよくやるミスか

**No。今回の事象は初心者的なミスではない。**

そう言える理由:

- 原因は upstream（Next.js 本体）の回帰であり、設定ミス・手順ミスではない
- 「Dependabot の PR を CI green で確認してマージする」は**教科書どおりの正しい運用**
- ロールバック可能な構造・失敗を検知する仕組み・リソース制限・ヘルスチェック・非 root コンテナといった要素は、既に整備されていた
- 現に、実務の production チームでも同じ地雷を踏みうる（`next build` が成功する以上、通常の CI では検知できない）

一方で、**個人開発・小規模運用で共通して残りやすい構造的なギャップ**は、今回いくつか露呈した。これは「ミス」ではなく「まだ着手していない領域」として認識するのが正確である。

| ギャップ | 内容 | 一般的な度合い |
|---|---|---|
| CI が「起動」を検証していない | ビルド成功＝OK と見なしていた | 個人・小規模で非常によくある |
| ステージング環境がない | main マージ ＝ 即本番 | 個人開発ではほぼ常態 |
| `:latest` タグ運用 | どの Pod がどのコミットか image tag から判別できない | 学習段階でよくある |
| デプロイが `rollout restart` | マニフェスト適用ではなく再起動によるデプロイ | 同上 |
| replicas: 1 | 冗長性なし（ただし今回は結果的に有利に働いた） | 個人インフラでは妥当な選択 |

「非エンジニアがやりがちなミス」に本当に該当するのは、むしろ次のような行動である。**今回はいずれにも当てはまらない**:

- エラーの意味を調べずに何度もリトライする／Pod を手で消して回る
- 原因を特定せず「とりあえず動くまで設定をいじる」
- 一次情報を確認せず AI やブログの回答をそのまま適用する
- ロールバックせず、本番で修正を試みる
- 失敗を記録に残さず、同じ穴を再度踏む

実際に取った行動は「A/B で再現 → 根本原因を特定 → 影響範囲を確認 → revert で確実に復旧 → 再発防止を設計」であり、これはインシデント対応の定石そのものである。

## 6. なぜ簡単にロールバックできたのか

「運が良かった」のではなく、**これまでに積み上げた規律が効いた**。順に分解する。

### 6.1 変更が 1 コミットに閉じていた（最大の要因）

方針「**1 PR = 1 関心事**」と **squash merge** の運用により、Next.js の更新は `d8cc4ca` という単一コミットに完全に閉じていた。だから `git revert d8cc4ca` の一発で戻せた。

もし「Next 更新 ＋ 機能追加 ＋ リファクタ」が同一 PR に混ざっていたら、revert は他の変更まで巻き戻すため、手作業での切り分けが必要になっていた。

### 6.2 変更対象が 2 ファイルだけだった

`package.json`（1 行）と `pnpm-lock.yaml` のみ。コンフリクトは lockfile だけで、`pnpm install --lockfile-only` が自動解決した。

### 6.3 lockfile による決定性

`pnpm-lock.yaml` ＋ `pnpm install --frozen-lockfile` により、**revert した時点の依存ツリーが完全に再現される**。「戻したのに動かない」が原理的に起きない。lockfile を持たない、あるいは `latest` を使う運用では、これが保証されない（方針「`latest` を使わない」が効いている）。

### 6.4 アプリケーションがステートレス

現時点の chumon-hub には **DB もマイグレーションも永続状態もない**。抽出フローは「アップロード → 一時ファイル → Gemini File API → 削除」で完結する。そのためコードを戻せば、それ以上考えることがない。

### 6.5 Kubernetes の RollingUpdate が旧 Pod を守った

`maxUnavailable: 0`（`replicas: 1` の丸め結果）により、**壊れたバージョンが一度もトラフィックを受け取らなかった**。readinessProbe が Ready を拒否し続けたためである。ダウンタイム 0 の直接の理由はこれ。

### 6.6 失敗が明示的にエラーになった

`rollout status --timeout=180s`（#157）があったため、GitHub Actions が赤くなり即座に気付けた。これがなければ、次にコードを変更するまで壊れたイメージが `:latest` に居座り続けていた。

> **重要な含意**: この 6 条件のうち **6.4（ステートレス）は Phase 5 で失われる**。DB とマイグレーションが入ると `git revert` だけでは戻らなくなる。§7 に対策を記載する。

## 7. 再発防止策

### 7.1 最優先: CI にコンテナ・スモークテストを追加（`ci/smoke-container`）

今回の穴を正面から塞ぐ。ボットレビュー（#288）でも同じ提案があり、方針は合意済み。

- `build-check` に `load: true` を追加し、ビルドしたイメージをローカルにロード
- `docker run -d` で起動
- `/` が 200 を返すまでポーリング（タイムアウト付き）
- 失敗時は `docker logs` を出力

設計上の論点:

- **検証パス**: `/` は `proxy.ts` の matcher（`/official-order/:path*`、`/api/:path*`）の外なので、Cloudflare Access なしで 200 が返る。K3s の readinessProbe と同一のパスで検証でき、本番と同値になる
- **環境変数**: 起動時に必須の変数があればダミー値を注入する（当然、実際の秘匿値は使わない）
- **コスト**: 既存の gha キャッシュを活かせば追加時間は数十秒程度

**この 1 つで、今回のクラス（ビルドは通るが起動しない回帰）は丸ごと捕捉できる。**

### 7.2 Next.js のマイナー更新に対する運用ルール

- マイナー以上の更新は、マージ前に **Dev Container で `pnpm build` ＋ standalone `node server.js` の起動確認**を手順として明文化する（7.1 が入れば CI が肩代わりする）
- Dependabot が #284 を再提案してくるため、upstream 修正までの一時 ignore を `.github/dependabot.yml` に入れるかは別途判断（入れる場合は**期限と解除条件をコメントで明記**し、放置による塩漬けを防ぐ）
- Next.js 側の修正状況を追跡し、修正後に 7.1 の CI 下で再挑戦する

### 7.3 イメージタグの不変化（中期）

`:latest` ＋ `rollout restart` を、**コミット SHA タグ ＋ `kubectl set image`（またはマニフェスト適用）**に変更する。得られるもの:

- 「今動いている Pod がどのコミットか」が確定する
- ロールバックが `kubectl rollout undo` で即座に可能になる（GitHub Actions を待たずに復旧できる）
- キャッシュ・タグの取り違えによる事故がなくなる

### 7.4 起動失敗を早く・正しく落とす（probe の見直し）

現状は `livenessProbe.initialDelaySeconds: 15` / `readinessProbe.initialDelaySeconds: 10` で運用している。**`startupProbe` を導入**すると、起動が遅いケースと起動できないケースを分離でき、CrashLoopBackOff の判定が速く・正確になる。あわせて `progressDeadlineSeconds` を明示すると、`rollout status` のタイムアウトと整合が取れる。

### 7.5 Phase 5 に向けた申し送り（重要）

**今回の「revert 一発で復旧」は、アプリケーションがステートレスである間だけ成立する。** Phase 5 で DB を導入した後は:

- マイグレーションを**前方・後方互換の 2 段階**（expand / contract）で設計し、コードだけ戻せる状態を維持する
- ロールバック手順を DB スキーマ込みで文書化する（[`../roadmap/PHASE4_PLUS_ROADMAP.md`](../roadmap/PHASE4_PLUS_ROADMAP.md) の非機能要件に紐づける）
- バックアップ／リストア手順を先に用意する（計画書 §3.3 に記載済みの項目）

この観点は **ロードマップ §4 の「可用性・信頼性」「データ整合性」に直結する**ため、Phase 5 詳細設計の入力として扱う。

## 8. 良かった点（維持すべき運用）

- **1 PR = 1 関心事 ＋ squash merge** → revert 可能性を担保した最大の要因
- **lockfile ＋ `--frozen-lockfile` ＋ `latest` 禁止** → 復旧の決定性
- **`rollout status --timeout`（#157）** → 沈黙する失敗を可視化。今回の検知そのもの
- **readinessProbe ＋ RollingUpdate** → 壊れたバージョンをユーザーに一切見せなかった
- **一次情報での検証** → 推測に頼らず A/B 再現で根本原因を確定させ、誤った対処（例: `output: 'standalone'` を外す）を回避した
- **ボットレビューの全件トリアージ** → 妥当な指摘（smoke test）は受け入れつつ、スコープ外として別 PR に切り出す判断ができた

## 10. 一言でまとめると

**upstream の回帰を踏んだが、「1 PR = 1 関心事」「lockfile による決定性」「失敗を明示的にエラーにする」という既存の規律が効いて、ユーザー影響ゼロで復旧できた。** 残った本質的な課題は 1 つだけで、**CI が「ビルドできる」までしか見ておらず「起動する」を見ていない**こと。ここを塞げば、同じクラスの事故は本番に到達しなくなる。
