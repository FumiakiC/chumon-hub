# インシデントレポート: 大量アップロードによる本番ノードの資源枯渇

**発生日**: 2026-09-19（JST） / 2026-09-18 23:00–23:34（UTC）
**対象**: chumon-hub（K3s on AWS Lightsail 2 vCPU / 2 GB RAM、`ghcr.io/fumiakic/chumon-hub:latest`）
**影響**: **サービス全断**（`replicas: 1`）。VM 全体が応答不能となり、Lightsail コンソールからの停止・起動が必要だった。データ損失なし（本アプリは現時点でステートレス）
**検知**: 利用中の応答停止。あわせて `Liveness probe failed: context deadline exceeded`
**復旧**: Lightsail コンソールから VM を停止・起動。ノード再起動後に Pod が再作成された
**重大度**: **高**（本番停止 ＋ 手動介入を要した ＋ 自動復旧しなかった）

## 2. 直接原因

**クロップ要求の同時実行数に上限が無く、144 件が同時に in-flight となってノードの資源を使い切った。**

`app/provisional-order/hooks/use-provisional-order.ts` の `handleFiles` は、選択されたファイルごとに `processCrop` を呼び、それぞれが独立した `POST /api/crop-title-block` を発行する。間隔は `setTimeout(..., Math.random() * 300)` のばらつきだけで、**上限は無い**。サーバー側にも受け止める仕組みが無い。

1 リクエストが同時に保持するもの:

| 保持物 | 概算 |
|---|---|
| 検証済みの原本 PDF バッファ | ファイルサイズぶん |
| pdfjs がデコードしたページ全体のビットマップ（RGBA 4 バイト/画素） | A2 ラスタで約 32 MB、A1 ラスタで約 64 MB |
| 出力キャンバス | 切り出し画素数 × 4 バイト |
| PNG バイト列と base64 文字列（1.33 倍） | 数 MB 規模 |

これが 144 件ぶん積み上がる。**Pod の `limits.memory` は 1Gi だが、ノードは 2 GB しかない。** k3s server・cloudflared・OS の使用分を引くと Pod に渡せる実質的な余力は 1 GB 前後で、**この上限はノードを保護していない**（「残り全部を使ってよい」に近い）。

CPU 側も同様で、pdfjs の解析・描画は純 JS のため単一のイベントループ上で競合する。`/` を 5 秒以内に返せず Liveness probe が失敗しているのはその結果である。

## 3. 根本原因（設計と判断）

### 3.1 #346 は引き金であって根本原因ではない

切り替え前のクロップは pdf-lib による CropBox / MediaBox の書き換えだけで、所要時間は数十 ms、メモリは PDF サイズ程度だった。144 件同時でも耐えられていた。#346 でラスタライズを導入したことで **1 件あたりのコストが時間・メモリとも 2 桁上がり**、もともと存在していた「同時実行制御の不在」という設計欠陥が顕在化した。

したがって本件を「C-1 切り替えの副作用」として片付けてはならない。同じ穴は、別の重い処理を本番経路に載せた瞬間に再び開く。

### 3.2 計画書は本リスクを予測し、先送りしていた

本書ではなくロードマップ側に、既に次の記載があった。

- 要件定義 §3.2「残存する弱点」: `replicas: 1` / memory limit 1Gi に対し **同時実行制御は Phase 4b の DoS ハードリミットへ申し送り**
- 基本設計 §4「エポック0 の申し送り（#301 由来）」: **同時実行制御を入れずに上限をさらに引き上げてはならない**

**見落としではなく、先送りの判断が誤っていた。** しかもその判断は「クロップが安価である」ことを暗黙の前提にしていた。#346 がその前提を壊した時点で申し送りを見直すべきだったが、行わなかった。

> **教訓（一般化）**: **既存処理のコストプロファイルを大きく変える PR は、「Phase X へ申し送り」と判断済みの項目の前提を壊していないか、着手時に必ず見直す。** 申し送りは判断の凍結ではなく、前提付きの延期である。

### 3.3 `MAX_RENDER_PIXELS` はこのメモリを守っていない

`lib/pdf/raster-crop.ts` の `MAX_RENDER_PIXELS`（16,000,000）は **出力キャンバスの画素数**を `createCanvas` の前に確認するものである。一方、実際にメモリを支配するのは**元 PDF に埋め込まれたラスタ画像のデコード**で、これは `page.render()` の実行中に起きる。したがって巨大な画像を埋め込んだ PDF は、この上限に一切到達しないままノードのメモリを消費できる。Phase 4b の DoS ハードリミットに、この観点が欠けている。

## 4. 未確定事項（要・一次情報での確定）

本書の以下は**推論であり、確定していない**。

| # | 未確定事項 | 確定方法 |
|---|---|---|
| 1 | ノードの死因がカーネル OOM killer か、スワップによるスラッシングか | `journalctl -k` の該当時間帯を `out of memory` / `killed process` で検索 |
| 2 | カーネル OOM killer が何を殺したか（k3s server / containerd 自身なら、Pod の limits 調整では防げない） | 同上 |
| 3 | スワップの有無 | `swapon --show` |
| 4 | Pod が一度も再起動していないか（`RESTARTS` が 0 なら「ノードだけが死んだ」が確定する） | `kubectl get pod -l app=chumon-hub` |
| 5 | 「自動復帰しなかった」の内容。取得したイベントでは、ノード再起動後に Pod が `Started` している | 再現時の観測、または `kubectl describe` の再取得 |
| 6 | 全断していた実時間 | Cloudflare 側のログ、または Pod のイベント時刻 |

`Reason: Unknown` / `Exit Code: 255` は OOMKilled の記録**ではない**。kubelet が正常な終了理由を書き残せなかった痕跡であり、ノード強制停止と整合する。Pod 単体が limits に当たって殺されていれば `Reason: OOMKilled` と明示される。

## 6. 再発防止策

### 6.1 最優先: `fix/crop-concurrency-limit`

**クライアント側の発行制限とサーバー側の in-flight 上限を、同じ PR で入れる。** クライアント制限だけでは「書き忘れたら漏れる」設計になる（タブを 2 枚開けば制限は二重になり、API は直接叩ける）。ロードマップ §2.7 の「境界の構造的強制」と同じ発想を、認可ではなく資源に適用する。

- クライアント: 解析側が既に採っている chunk size 2 と揃える
- サーバー: `/api/crop-title-block` の同時実行数に上限を設け、超過は 429

### 6.2 `fix/k8s-resource-guard`

- `limits.memory` をノードの余力に見合う値へ引き下げ、Pod 単体の暴走がノードを道連れにしない状態にする
- `livenessProbe` を軽量なエンドポイントへ変更（`proxy.ts` の matcher 除外とセットで設計）
- `startupProbe` / `progressDeadlineSeconds` の導入（前回インシデントのアクションアイテム #5 と統合してよい）

### 6.3 `MAX_RENDER_PIXELS` の穴を Phase 4b の DoS ハードリミットへ起票

出力画素数ではなく、**デコード対象の画素数**にも上限が要る。

### 6.4 運用の暫定回避（6.1 が入るまで）

1 回のアップロードを 10 枚程度に分ける。

### 6.5 Phase 5 への含意

**「図面解析はブラウザを閉じても継続する非同期・サーバーサイド処理にする」という決定（要件定義 §3.2）が、実運用によって裏付けられた。** 144 枚を同期リクエストで捌く設計には無理がある。6.1・6.2 はジョブ基盤が入るまでの暫定措置という位置づけであり、恒久対策はジョブ基盤側にある。

## 8. 一言でまとめると

**#346 は引き金であって根本原因ではない。根本原因は、同時実行制御の不在という既知の欠陥を Phase 4b へ先送りしたまま、その先送り判断の前提（クロップは安価）を壊す変更を本番に入れたことである。** 計画書は risk を予測していたので、必要だったのは新しい洞察ではなく、**申し送りを読み直すタイミングの規律**だった。
