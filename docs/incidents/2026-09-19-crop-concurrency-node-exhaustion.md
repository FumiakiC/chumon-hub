# インシデントレポート: 大量アップロードによる本番ノードの停止

**発生日**: 2026-09-19（JST） / 2026-09-18 23:00–23:35（UTC。以下、時刻は UTC）
**対象**: chumon-hub（K3s on AWS Lightsail `t3.small` 2 vCPU / 2 GB RAM、`ghcr.io/fumiakic/chumon-hub:latest`）
**影響**: **サービス全断**（`replicas: 1`）。約15分（23:20 頃〜23:36 頃）。データ損失なし（本アプリは現時点でステートレス）
**検知**: 利用中の応答停止。あわせて `Liveness probe failed: context deadline exceeded`
**復旧**: Lightsail コンソールから再起動 → 回復せず → 停止・起動（計2回の操作）
**重大度**: **高**（本番停止 ＋ 手動介入を要した ＋ コントロールプレーンごと停止した）

> 本書は当初 `journalctl` 取得前の推論で書かれ、「ノードのメモリが枯渇した」と結論していた。
> その後の一次情報により**その分析は誤りであることが判明したため、本版で全面的に訂正した**。

## 2. 直接原因

**ノード全体が資源競合に陥り、コントロールプレーン（k3s）が動作を停止した。**
アプリはコンテナに設定された上限の内側に収まっていたにもかかわらず、ノードは守られなかった。

### 2.1 アプリは上限を超えていない（確定）

| 観測 | 意味 |
|---|---|
| 障害時の boot にカーネル OOM も cgroup OOM も**1行も無い** | **アプリは `limits.memory: 1Gi` を一度も超えていない**。超えていれば `Memory cgroup out of memory` が記録される |
| `limits.cpu: '1000m'` | 2 コアのうち 1 コアが上限。**アプリが CPU でノードを食い尽くすことは構造的にできない** |
| コンテナ終了は `Reason: Unknown` / `Exit Code: 255` | OOMKilled でも liveness 起因の kill でもない。ノード停止に巻き込まれた記録 |
| `RESTARTS: 1` | ノード停止による1回のみ。liveness の `failureThreshold: 3` には到達していない |

### 2.2 それでもノードは止まった（確定）

| 観測 | 意味 |
|---|---|
| 23:18:52 の COMPACT が 45.2ms（通常 2.6〜3.6ms） | 競合の最初の兆候。約15倍の悪化 |
| 23:20:20 以降 k3s のログが途絶 | 定期処理が回らない＝コントロールプレーン停止 |
| SIGTERM から SIGKILL まで 81 秒 | 停止操作の時点でも k3s は応答できない状態 |
| カーネルログが 23:00:35〜23:33:45 で完全に無音 | ハードウェアもカーネルも健全。純粋な資源競合 |

### 2.3 なぜ上限を設けても守られなかったのか

- **`limits` の総和がノード容量を超えている。** カーネル取得後の実使用可能メモリは約 1.4 GB
  （`Memory: 1434212K/2037804K available`）。そこにアプリの `limits.memory: 1Gi` を置き、
  さらに k3s 自身が `1.1G memory peak` に達しうる。**合計は構造的に容量を超える。**
- **スケジューラは `requests` しか見ない。** 本 Pod の requests は `100m` / `256Mi` であり、
  limits の超過はスケジューリング上まったく検知されない。
- **k3s に `--system-reserved` / `--kube-reserved` が設定されていない。** OS とコントロール
  プレーンのための取り分が確保されておらず、ワークロードがそこへ食い込める。

### 2.4 当初の分析の誤り（記録として残す）

初版では「144 件が同時に in-flight となり、デコード済みビットマップが 144 件ぶん積み上がって
ノードのメモリを使い切った」と書いたが、**これは誤りである**。

**Node.js は単一スレッドであり、pdfjs の描画は直列に実行される。** したがって同時にデコード
されているビットマップは常に 1 枚で、残りのリクエストは数 MB のアップロード済みバッファを
抱えて待っているにすぎない。ピークメモリは初版の見積り（約 1.5 GB）より桁違いに小さい。
実際、cgroup OOM は発生していない。

一方で**直列であること自体が問題**である。1 件 1〜3 秒の同期的な描画が連続すると、イベント
ループは解放されず、`/` を 5 秒以内に返すことができない。liveness probe の失敗はその帰結である。

## 3. 根本原因（設計と判断）

### 3.1 #346 は引き金であって根本原因ではない

切り替え前のクロップは pdf-lib による CropBox / MediaBox の書き換えだけで、所要時間は数十 ms、
メモリは PDF サイズ程度だった。144 件同時でも耐えられていた。#346 でラスタライズを導入したことで
**1 件あたりのコストが 2 桁上がり**、もともと存在していた欠陥（同時実行制御の不在、リソース上限が
ノード保護になっていないこと）が顕在化した。

したがって本件を「C-1 切り替えの副作用」として片付けてはならない。同じ穴は、別の重い処理を
本番経路に載せた瞬間に再び開く。

### 3.2 計画書は本リスクを予測し、先送りしていた

ロードマップ側に、既に次の記載があった。

- 要件定義 §3.2「残存する弱点」: `replicas: 1` / memory limit 1Gi に対し **同時実行制御は Phase 4b の DoS ハードリミットへ申し送り**
- 基本設計 §4「エポック0 の申し送り（#301 由来）」: **同時実行制御を入れずに上限をさらに引き上げてはならない**

**見落としではなく、先送りの判断が誤っていた。** しかもその判断は「クロップが安価である」ことを
暗黙の前提にしていた。#346 がその前提を壊した時点で申し送りを見直すべきだったが、行わなかった。

> **教訓（一般化）**: **既存処理のコストプロファイルを大きく変える PR は、「Phase X へ申し送り」と
> 判断済みの項目の前提を壊していないか、着手時に必ず見直す。** 申し送りは判断の凍結ではなく、
> 前提付きの延期である。

### 3.3 リソース上限が「ノードの保護」として設計されていなかった

`limits` は「1つの Pod が使いすぎないための上限」であり、**複数の Pod と OS とコントロール
プレーンの合計がノードに収まることは、まったく保証しない**。本件はその区別が設計に反映されて
いなかった事例である。`--system-reserved` / `--kube-reserved` と、limits 総和の上限管理が要る。

### 3.4 `MAX_RENDER_PIXELS` はメモリ上限として機能していない（潜在的欠陥）

`lib/pdf/raster-crop.ts` の `MAX_RENDER_PIXELS`（16,000,000）は **出力キャンバスの画素数**を
`createCanvas` の前に確認するものである。一方、実際にメモリを支配するのは**元 PDF に埋め込まれた
ラスタ画像のデコード**で、これは `page.render()` の実行中に起きる。巨大な画像を埋め込んだ PDF は
この上限に一切到達しないままメモリを消費できる。

**本件の直接原因ではない**（cgroup OOM は発生していない）が、独立した欠陥として残っている。
Phase 4b の DoS ハードリミットにこの観点が欠けている。

## 4. 確定した事項と、確定できなかった事項

### 4.1 確定（一次情報による）

| # | 事項 | 根拠 |
|---|---|---|
| 1 | カーネル OOM も cgroup OOM も発生していない | 障害時 boot の `journalctl -k` に該当ログが皆無 |
| 2 | swap は無効（`Swap: 0B`） | `swapon --show` / `free -h` |
| 3 | `RESTARTS: 1` はノード停止に由来する。liveness による再起動でも OOMKilled でもない | AGE 3h17m と `RESTARTS 1 (163m ago)` の逆算が Pod 作成 23:00・終了 23:34 と一致 |
| 4 | 「自動復帰しなかった」の内容は、再起動1回（27秒で判断）→ 停止・起動、の2回の操作 | journal の boot 一覧と利用者報告が一致 |
| 5 | ノードはクラッシュしていない。2回とも正常な `systemd-poweroff` で終了している | systemd ログ |
| 6 | コントロールプレーンは 23:20:20 以降停止していた | 5分周期の COMPACT と 10分周期の cidrallocator の欠落 |

### 4.2 確定できなかった事項

**資源競合の支配要因（メモリ逼迫／CPU／ディスク I/O）は特定できない。**

- カーネルはこの種の緩やかな劣化をログに出さない（OOM に至らないページキャッシュの追い出し、
  CFS スロットリング、I/O 待ちのいずれも無言で進行する）
- **本ノードには資源状況の履歴が残らない。** metrics-server は稼働しており `kubectl top` で
  現在値は取得できる（2026-09-19 の #347 適用作業で確認。導入から 251 日）。しかし保持されるのは
  直近の値のみで時系列が残らないため、障害時点の CPU / メモリ / I/O を事後に参照できない

> **訂正（2026-09-19）**: 本項は当初「metrics-server も node_exporter も未導入」と書いていたが、
> これは誤りである。#347 の適用作業で metrics-server の稼働を確認した。欠けているのは収集の仕組み
> ではなく**履歴の保持**であり、再発防止策（§6.5）と AI#5 の内容もそれに合わせて修正した。

これは調査の限界ではなく**設備の欠落**である。同じことが起きても次回も特定できない。
可観測性の整備を再発防止策に含める（§6.5）。

## 6. 再発防止策

### 6.1 `fix/crop-concurrency-limit`

**クライアント側の発行制限とサーバー側の in-flight 上限を、同じ PR で入れる。** クライアント制限
だけでは「書き忘れたら漏れる」設計になる（タブを 2 枚開けば制限は二重になり、API は直接叩ける）。
ロードマップ §2.7 の「境界の構造的強制」と同じ発想を、認可ではなく資源に適用する。

- クライアント: 解析側が既に採っている chunk size 2 と揃える
- サーバー: `/api/crop-title-block` の同時実行数に上限を設け、超過は 429

**効く理由（初版から訂正）**: メモリのピーク抑制ではない。**キューの滞留を抑え、1 件ずつ確実に
完了させて進捗を可視化すること**、およびサーバーが抱える未処理リクエストの総量を減らすことにある。
**イベントループの占有そのものは同時実行制限では解けない**（§6.3）。

### 6.2 `fix/k8s-resource-guard`

**本体は k3s の予約設定であり、`limits.memory` の引き下げではない。**

- k3s に `--system-reserved` / `--kube-reserved` を設定し、OS とコントロールプレーンの取り分を確保する
- `limits` の総和がノード容量を超えない状態にする（アプリ側 limits の見直しを含む）
- `livenessProbe` の対象を `/` から軽量なエンドポイントへ変更（`proxy.ts` の matcher 除外とセットで設計）
- `startupProbe` / `progressDeadlineSeconds` の導入（前回インシデントのアクションアイテム #5 と統合してよい）

### 6.3 描画をイベントループから逃がす（設計検討）

pdfjs の描画は CPU バウンドかつ同期的で、Node の単一スレッドを占有する。`worker_threads` や
別プロセスへ逃がせば、HTTP のイベントループは解放され、probe も他のリクエストも生き続ける。
**本件で liveness が落ちた直接の機序への唯一の構造的対策**であり、Phase 4b / Phase 5 の設計材料とする。

### 6.4 `MAX_RENDER_PIXELS` の穴を Phase 4b の DoS ハードリミットへ起票

出力画素数ではなく、**デコード対象の画素数**にも上限が要る。

### 6.5 可観測性の整備

- **アプリ側**: クロップ経路の所要時間と出力バイト数を、本番でも残るレベルの構造化ログに出す
- **ノード側**: メトリクスの**時系列保持**を導入し、障害時の CPU / メモリ / I/O を事後に参照できる
  ようにする。metrics-server は稼働しているので現在値は取れるが、履歴が残らない。今回、支配要因を
  特定できなかった直接の原因がこれである
- **journal**: 障害時の boot のログは保持されていた（persistent）。この点は問題なかった

### 6.6 運用の暫定回避（6.1 が入るまで）

1 回のアップロードを 10 枚程度に分ける。

### 6.7 Phase 5 への含意

**「図面解析はブラウザを閉じても継続する非同期・サーバーサイド処理にする」という決定
（要件定義 §3.2）が、実運用によって裏付けられた。** 144 枚を同期リクエストで捌く設計には無理がある。
6.1〜6.3 はジョブ基盤が入るまでの暫定措置という位置づけであり、恒久対策はジョブ基盤側にある。

## 8. 一言でまとめると

**アプリはコンテナの上限を一度も超えていない。それでもノードは止まった。**
`limits` は 1 つの Pod を抑えるだけで、OS とコントロールプレーンを含めた合計がノードに収まることを
保証しない。そこに、同時実行制御の不在という既知の欠陥を Phase 4b へ先送りしたまま、その先送りの
前提（クロップは安価）を壊す変更を本番へ入れた。

計画書はリスクを予測していたので、必要だったのは新しい洞察ではなく、**申し送りを読み直す
タイミングの規律**だった。そして支配要因を特定できなかったことは、**本番の可観測性が
整備されていないという別の欠陥**を露わにした。
