# ADR-1: 実行基盤を k3s（AWS Lightsail）から Cloud Run へ移す

- 状態: 決定 2026-10-11（Cloud Run の採用と、Phase 4b の前に移行する時期を決めた。本番の切り替えの承認は含まない）
- 関連: [ADR-3](ADR-3-sequencing.md)（移行順序）／[ADR-4](ADR-4-base-image.md)（本 ADR の決定で再検討トリガ 1 が発火した。[ADR-6](ADR-6-base-image-glibc.md) で置換）／[ADR-5](ADR-5-database.md)（DB の接続形態）／計画書 基本設計 §4「移行エポック詳細計画」（移行の順序と切り替えの条件）／計画書「決定事項と未決事項」の「実行基盤（Cloud Run 化）」「STG 環境」「本番の秘匿（管理上の正と実行時の供給元）」「ノードのリソース保護」「非同期ジョブ実行」「マニフェスト適用の自動化と Secret 管理」／[2026-09-19 インシデント](../incidents/2026-09-19-crop-concurrency-node-exhaustion.md) §5 の欠陥 #5

## 背景 / 課題

現行の本番は Docker → GHCR → k3s（AWS Lightsail の単一ノード）で、入口は Cloudflare Access + Tunnel。

## 選択肢

- Cloud Run（サーバレス従量・scale-to-zero。Next.js は `output: "standalone"` で素直に載る）
- GKE Autopilot（k8s を継続したい場合の中間解）
- Firebase App Hosting
- 現状維持（インスタンスの増強を含む）

## 選択肢の比較（2026-10-11。#385 のレビューを受けて記録）

比較の軸は、運用の負担、費用（今の低いトラフィックで）、入口と安全性、将来の非同期ジョブ・DB・ストレージとの接続、ロックインの 5 つ。料金と仕様は 2026-10-11 に公式文書で確かめた値で、変わりうる。

**Cloud Run（採用）**

- 運用: ノードとクラスタを持たない。管理するのは、サービスの設定・IAM・入口で、OS や k8s の更新は無い。
- 費用: 既定のリクエスト課金では、要求の処理中と起動・終了時だけ CPU とメモリに課金され、最小インスタンスではないアイドルのインスタンスには課金されない。毎月の無料枠もある。STG も最小インスタンス数 0 で置ける。一方で、入口の保護のために置く部品（ロードバランサーなど）は固定費になる。
- 入口と安全性: 弱点。`run.app` の URL が公開されるため、Cloudflare Access だけでは迂回を防げず、ingress の制限と IAM 認証、またはロードバランサー側の origin 認証の組み合わせが要る（下記「入口」）。
- 将来の接続: 非同期ジョブ・DB・ストレージは、マネージドなサービス（キュー、DB、オブジェクトストレージ）とつなぐ形になる。手段は Phase 4.5 の ADR（DB は ADR-5）で決める。
- ロックイン: 中。コンテナイメージは移せるが、サービスの設定・IAM・入口は GCP に固有。

**GKE Autopilot**

- 運用: ノードは Google が管理するが、クラスタと k8s のマニフェストの管理は残る。repo の `k8s/` と本番の乖離（[`../ops/k3s-live-state.md`](../ops/k3s-live-state.md)）と同じ種類の問題を抱え続ける。
- 費用: 一般用途のワークロード（Pod 単位の課金）では、実行中の Pod が要求した CPU・メモリ・一時ストレージに、秒単位で課金される。アプリは常時起動なので、アイドルでも課金が続く。クラスタの管理料（1 クラスタ 1 時間あたり 0.10 USD）は、請求先アカウントごとに月 74.40 USD の無料枠のクレジット（1 クラスタ分）で相殺されるが、同じ請求先アカウントに STG のクラスタを置けば、2 つ目には管理料がかかる。
- 入口と安全性: 強み。Cloudflare Tunnel を継続利用する構成（cloudflared を Pod として動かす）を取れ、公開の入口を持たずに済む。既存のマニフェストがそのまま適合するかは、移行するときに確かめる。
- 将来の接続: Cloud Run と同じマネージドなサービスにつなげるほか、クラスタの中にワーカーなどを置く自由度が高い。その分、運用は増える。
- ロックイン: 低。マニフェストとイメージは、他の k8s へ移せる。

**Firebase App Hosting**

- 運用: ソースからのビルドを使えば最も少なく、指定したブランチへの push でビルドとデプロイが走る。自前のイメージを持ち込む場合、イメージのビルドは既存の CI などで行い、App Hosting のリソースとデプロイを Terraform で管理する経路がある。実体は Cloud Build・Cloud Run・Cloud CDN で、前段に Google Cloud のロードバランサーが入る。
- 費用: 実体のサービスの利用量で課金され、Blaze プランが要る。
- 入口と安全性: 実体が Cloud Run なので、Access の迂回を防ぐ課題は Cloud Run と同じく残る。前段に App Hosting のロードバランサーと CDN が入るため、Cloud Run を直接使う場合と同じ構成を取れるかは確認していない（下記 (c)）。
- ビルドとデプロイ: 既定はソースからのビルド（GitHub 連携・CLI・アーカイブのアップロード）で、Cloud Build がフレームワークのビルドを実行し、buildpacks がコンテナを作る。ほかに Terraform を使えば、自分でビルドしたコンテナイメージを、ソースから再ビルドせずに直接デプロイできる。つまり、既存の `Dockerfile` から作ったイメージを持ち込む経路はある。ただし、次の 3 点は確認していない。(a) このアプリの本番イメージ（Next.js の standalone 出力、`proxy.ts`、ネイティブ依存の `@napi-rs/canvas` を含む）が、App Hosting の実行環境でそのまま動くか。(b) STG で確かめたのと同じ digest を、環境の間で昇格させられるか。(c) Access の迂回を防ぐ入口の構成を取れるか。
- ロックイン: 高い。ソースからのビルドでは、ビルドの仕組みと設定が Firebase に依存する。自前のイメージを持ち込めばイメージは移せるが、バックエンドの設定は Firebase に固有。

**現状維持（Lightsail のインスタンスの増強を含む）**

- 運用: 最も重い。OS と k3s の更新、ノードの資源の予約（#347）、マニフェストの照合を自分で続ける。単一ノードは、再起動すれば全断のまま（インシデントの欠陥 #5）。
- 費用: 定額で予測しやすい。増強すれば月額が上がる。
- 入口と安全性: 今の Tunnel をそのまま使え、公開の入口を持たない。
- 将来の接続: DB・ジョブ基盤を同じノードに載せると、2GB では破綻する（下記「2026-09-19 追記」）。増強しても単一ノードのままで、外部のマネージドなサービスとつなぐなら、移行と同じ設計が要る。
- ロックイン: 最も低い。

**比べていない選択肢**: AWS のマネージドなコンテナ実行基盤（ECS on Fargate など）は、選択肢に挙げておらず、比べていない。Gemini とは API キーでつないでいるため、Google Cloud を選ぶ技術上の必然は無い。再検討するときは、ここから比べ直す。

**決め手**

- 現状維持に対して: ノードの運用と、単一ノードの全断を無くせる。DB・ジョブ基盤を載せる段階で 2GB が破綻する問題は、増強では先送りにしかならない。
- GKE Autopilot に対して: クラスタとマニフェストの管理が残らない。常時起動の Pod の課金とクラスタの管理料が無く、STG を最小インスタンス数 0 で安く置ける。入口では GKE Autopilot が有利（Tunnel を継続利用する構成を取れる）で、これは Cloud Run の弱点として受け入れ、再検討トリガ 1 で扱う。
- Firebase App Hosting に対して: App Hosting の実体は Cloud Run なので、入口・メモリ上のファイルシステム・タイムアウトといった Cloud Run の課題は、そのまま残る。既存のイメージを持ち込む経路はあるが、(a)〜(c) は確認していない。今回は、既存のイメージを用い、実行設定・IAM・入口・digest の昇格を Cloud Run の構成として直接管理する方針を優先する。App Hosting の追加機能を必要とする要件は、現時点では挙がっていない。
- 入口の要件が成立しない場合（再検討トリガ 1）は、Tunnel を継続利用する GKE Autopilot などを再比較する。代替候補の優先順位は、その時点の費用・運用負担・実装上の制約から決める。

## 決定と理由（2026-10-11）

**Cloud Run を採用し、Phase 4b より前に移行する。** 計画書の当初の予定（Phase 4.5 で本 ADR を決め、Phase 5 の直前に移行する）を前倒しする。移行は計画書のエポック表 2b「移行エポック」として行う。

Cloud Run を選んだ理由は、上記「選択肢の比較」の「決め手」。

移行を早める理由（どのマネージドな基盤を選んでも共通する）:

- DB が無い今なら、k3s を残して並行稼働し、入口の向き先を戻すだけで切り戻せる（条件付き。計画書 基本設計 §4「移行エポック詳細計画」の「切り戻し」）。DB の導入後は、スキーマとデータを戻せないため、切り戻しが難しくなる。
- 本 ADR の決定待ちにしていた k3s 向けの作業（Secret の注入、マニフェストの自動適用、メトリクスの時系列保持、ベースイメージの見直し）を、k3s 上に作り込まずに済む。
- 2GB の単一ノードが落ちるリスク（下記「2026-09-19 追記」）が今も残っている。
- Phase 4b の DoS ハードリミット（タイムアウト・メモリ・並列度）を、移行後の制約のもとで一度に決められる。

**採用の決定と、本番の切り替えの承認を分ける。** 本 ADR が決めるのは、Cloud Run の採用と移行の時期までである。本番の切り替えは、入口の保護・容量・タイムアウト・Gemini のクォータ・費用・可観測性・切り戻しの条件を STG と並行稼働で検証してから、owner が承認する。条件の正は計画書 基本設計 §4「移行エポック詳細計画」の「切り替えの条件」。検証で重大な不成立が判明した場合は、切り替えを止めて本 ADR を再検討する（下記「再検討トリガ」）。

## 移行の設計で扱う判断材料（2026-10-11）

計画書の「切り替えの条件」に対応する、Cloud Run 固有の事項。入口の構成と設定値は、STG の試行（設定を調整するための測定）で決める。合否を判定する受け入れの基準（容量・費用・初回応答・Gemini のエラー率など）は、試行の結果ではなく業務上の要件から決め、受け入れの測定の前に owner が承認して本 ADR に記録する（計画書 基本設計 §4「移行エポック詳細計画」の「受け入れの基準」）。

- **入口**: Cloudflare を前段に置くだけでは、公開された `run.app` の URL への直接アクセスを防げない。Cloud Run の ingress を `All` にすると `run.app` の URL にインターネットから直接届き、`Internal and Cloud Load Balancing` にすると直接の要求は拒否される。ただし ingress はネットワークの制御で、ロードバランサーの入口を誰でも使えるなら Access を迂回できる。公式も ingress と IAM 認証の併用を勧めている。候補は「Access → 認証プロキシ → IAM 認証必須の Cloud Run」と「Access → ロードバランサー → ingress を制限した Cloud Run＋ロードバランサー側の origin 認証」で、STG で実証して選ぶ。
- **タイムアウト**: Cloud Run はリクエストのタイムアウトで 504 を返しても、要求を処理していたインスタンスを止めず、コードは打ち切られた要求の処理を続けうる（タイムアウトの既定は 5 分、最大 60 分）。Next.js の `maxDuration` は、デプロイ先のプラットフォームが実行上限に使う値で、standalone が処理を打ち切る保証にはならない。期限はアプリ側で持ち、アプリ・Gemini の呼び出し・Cloud Run・前段のプロキシで揃える。
- **同時実行数**: インスタンスあたりの同時実行数の既定は、コンソールで作ると 80、gcloud CLI や Terraform で作ると vCPU 数 × 80（サービスの作成時だけ適用される）。プロセスごとの上限（クロップの in-flight 上限 2 など）は、インスタンスが N 台に増えれば全体で最大 N 倍になる。同時実行数と最大インスタンス数は明示し、既定に任せない。最大インスタンス数は、トラフィックの急増などで一時的に超えることがあり、厳密な上限にはならない（公式は通常、サービス単位での設定を勧めている）。同時実行数の制限は、Gemini の RPM・TPM の制御にもならない。
- **メモリ上のファイルシステム**: 書き込み可能なファイルシステムはメモリ上にあり、書き込みはインスタンスのメモリを使い、インスタンスが止まると消える。`os.tmpdir()` への一時保存（`lib/ai/pipeline/upload.ts`）は、メモリの見積もりに含めるか、サイズ上限付きのメモリ上のボリュームに置く。
- **費用と初回応答**: 入口の保護のために置くロードバランサーなどの費用は、scale-to-zero では消えない。Artifact Registry・Secret Manager・ログ・通信・Gemini・移行中の Lightsail も別にかかる。入口を含めた月額費用の上限と、無負荷からの初回ログイン・初回クロップ・初回抽出の所要時間の上限は、受け入れの基準として測定の前に決める（初回は JWKS の取得と PDF ライブラリの初期化が重なる）。受け入れの測定では、試行とは別に見積もりと所要時間を測り、承認済みの上限と比べる。STG と本番で入口を共有するかどうかも比べて決める。予算の通知は支出の上限ではない。
- **Gemini の API キーとクォータ**: Cloud Run のプロジェクトと、キーが属する Gemini のプロジェクトは別に選べる。Gemini API のレート制限は API キーごとではなくプロジェクト単位でかかり、モデルごとに RPM・TPM・RPD などの軸がある。STG のキーを同じプロジェクトに作れば、資格情報は分かれてもクォータは共有になり、並行稼働中は旧本番（k3s）の負荷も同じクォータを使う。扱いは計画書 基本設計 §4「移行エポック詳細計画」の「Gemini の API キー」。
- **秘匿**: 管理上の正は 1Password とし、実行時の供給元は Secret Manager を第一候補とする（計画書「決定事項と未決事項」の「本番の秘匿（管理上の正と実行時の供給元）」）。Cloud Run は環境変数として渡す Secret をインスタンスの起動時に解決し、公式は `latest` ではなく特定のバージョンに固定することを勧めている。
- **構成のコード管理**: サービスの設定・IAM・入口・Secret の参照を repo で管理し、緊急の手動変更を repo に戻す手順を設ける。コンソールで変えれば、k3s で起きたマニフェストの乖離（[`../ops/k3s-live-state.md`](../ops/k3s-live-state.md)）が再発する。管理の手段は移行エポックで決める。
- **退路**: Docker イメージは GKE へそのまま移せる。
- **k3s 側の参考**: k3s 同梱の Traefik と `svclb-traefik` は、chumon-hub の経路に使われないまま 2GB ノードのメモリを使っている（[`../ops/k3s-live-state.md`](../ops/k3s-live-state.md)）。撤去までの短い期間のために、k3s の構成は変えない。

決定時の訂正: 検討中の「留意点」にあった「`/tmp` は揮発する（短命の利用なら問題ない）」は、短命でもメモリを使う点を見落としていたため、上記の「メモリ上のファイルシステム」に改めた。「秘匿情報は Secret Manager へ移す」は、管理上の正と実行時の供給元を分けて上記の「秘匿」に改めた。「cold start は、イメージの縮小と、必要時の `min-instances=1` で抑える」は、初回応答の上限（受け入れの基準）を決めてから手段を選ぶことにした。

## 2026-09-19 追記（実行基盤のサイズ）

#347 の適用で、Lightsail `t3.small`（2 vCPU / 2GB）のメモリ配分は「k3s が通常時（実測 764Mi、Pod 以外の合計 1025Mi）にとどまる前提」でのみ成立することが確定した。
Allocatable は `894996Ki`（約 874Mi）で、アプリ 512Mi + coredns 170Mi + 上限なしの system pods で 78% を占める。
`*-cgroup` による強制を行わない以上 **k3s 自身の使用量は制限されず、k3s が過去の peak（約 1.1G）まで振れた場合に耐える配分はこのノード上に存在しない**。

つまり #347 が保証するのは「アプリが原因でノードが死なない」までであり、「ノードが死なない」ではない。
DB・ジョブ基盤（Phase 5）を載せる段階では、この 2GB が先に破綻する。

## 影響範囲 / 依存

- [ADR-3](ADR-3-sequencing.md) の ① にあたる。Cloudflare Tunnel は k3s とともに撤去し、Cloudflare Access は ADR-3 の ③（アプリ内認証への移行）まで残す（[ADR-2](ADR-2-in-app-identity.md)）。
- [ADR-4](ADR-4-base-image.md) の再検討トリガ 1 が発火した。本番のベースイメージの収束方向は、移行エポックで STG の試行の前に決める。2026-10-17 に [ADR-6](ADR-6-base-image-glibc.md) で決め、ADR-4 を置換した（実装と検証は別の PR で、STG の試行の前に終える）。
- 計画書「決定事項と未決事項」の「マニフェスト適用の自動化と Secret 管理」は行わず、k3s の撤去とともに終了する。
- デプロイ経路（`deploy.yml`）は、STG で確かめたのと同じイメージの digest を本番へ昇格させる方式に変える。ブランチ戦略・デプロイの流れ・本番の権限の分離は [`../ops/branch-and-deploy.md`](../ops/branch-and-deploy.md) で定める。
- 非同期ジョブ基盤（計画書 基本設計 §3-4）と可観測性ベースラインは、Cloud Run を前提に Phase 4.5 の ADR で決める。

## 次アクション / 再検討トリガ

次アクション: 計画書 基本設計 §4「移行エポック詳細計画」を進める。受け入れの基準（受けるべき負荷と、Phase 5 で DB・ジョブ基盤とつなぐことを見込んだ余裕を含む容量、費用の上限、初回応答の上限、Gemini のエラー率・待ち時間・再試行の上限）は、受け入れの測定の前に owner が承認して本 ADR に記録する。入口の構成と設定値は STG の試行で決めて記録する。基準を後から変えるときは、理由を記録して owner が承認し直し、受け入れの測定をやり直す。

再検討トリガ: 移行エポックの検証で次のいずれかが判明したら、切り替えを止めて本 ADR を再検討する。

1. 入口を迂回されない構成が、承認済みの費用の上限と、許容できる運用の負担の範囲で取れない。
2. 受け入れの測定で、容量・初回応答・費用が、事前に承認した基準を満たさない。
3. k3s・本番の Cloud Run・STG を合わせた負荷を、Gemini のクォータを含めて、事前に承認したエラー率・待ち時間・再試行の上限の範囲で受けられない。
4. 切り戻しの条件を満たせない。
