# 第1部 要件定義

## 1. 目的とスコープ

買い手（発注側）として、1案件を **採番から支払い完了まで** 一貫して扱う発注ライフサイクル基盤を完成させる。

- 入力2チャネル: 機械図面の表題欄（仕様の根拠）／見積書（価格の根拠）。両者は同一案件の別タイミングの入力。
- 仮注文書（単価・納期＝協議中）→ 見積確定後、**同一注文番号を引き継いで** 本注文書を発行。
- スコープ外: メール自動送受信（所有者決定）。その他のスコープ拡大は所有者判断。

## 2. 業務要件（ステータス棚卸し）

### 2.1 ライフサイクル状態（ヘッダ＝案件レベル）

```
起案（draft・採番）→ 承認待ち（多段: 一次承認 → … → 最終承認）→ 社内承認済（発注待ち）
  → 仮注文発行 → 請書受領（仮）→ 見積受領 → 本注文発行 → 請書受領（本）
  → …（進捗は明細×数量から導出）… → クローズ（支払完了）
                                      └→ キャンセル（**境界あり**。下記参照。番号は残す）
```

- **社内決裁と購買（発注）の分離**: 他社導入時の職務分掌（設計部門＝起案、購買部門＝発注）に対応するため、「承認待ち（多段）」「社内承認済（発注待ち）」を正式な状態として持つ。承認フローは**多段・可変**（一次承認、最終承認など段数をテナント設定で変更可能）な構造とする。
- **自社運用（実質単一ユーザー）**: 起案・承認・発注の全ロールを単一ユーザーに付与した場合、承認ステップは**自動通過してシームレスに遷移**する（ステップの存在を意識させない）。ワークフローの有無で分岐する2系統のコードを作らず、「全権ユーザーなら即時承認」の縮退として実装する。
- 差し戻し（Reject）は起案へ戻す。条件付き承認を許容する（いずれもコメント必須。§基本設計 1 の ApprovalLog に記録）。
- 【要決定】承認フローを**仮注文発行前と本注文発行前の両方**に要求するか、仮のみ／本のみか（テナント設定候補）。

- **キャンセルの境界**: 単純な「キャンセル状態への遷移」を許容するのは**原則「未検収まで」**（境界の厳密な位置＝本注文発行後を含めるか等は Phase 5 詳細設計で確定）。検収・請求・支払が発生した後の取り消し・修正は状態遷移では行わず、**赤黒処理**（マイナス数量の返品明細・相殺請求・相殺支払を立てる）により数量会計上で相殺する。検収後・支払後のデータ整合性を状態の巻き戻しで壊さないための要件。
- **変更注文（版管理）**: 発行済み注文書の内容変更（検収前の数量・単価・仕様変更）は、発行済み版を書き換えるのではなく **rev（版番号）を上げた新版を発行**し、取引先へ再交付する。旧版は不変のまま保持（証憑不変性と整合）。仮→本の遷移も「同一注文番号の版遷移」の一種としてこの版管理に一般化する。検収後の変更は版ではなく赤黒処理の領分。

- **請書受領**を正式な状態として持つ（現行帳票の下部に注文請書があり、取引先が納期記入・押印して返送する運用が実在する）。
- **進捗系（納品・検収・請求・支払）はヘッダの stored state にしない**。分納・一部検収が存在するため、ヘッダ単一状態は不整合の温床になる。進捗は明細×数量の集計からの**導出値**とする（§基本設計 2.3）。

### 2.2 多重度（確定事項）

| 関係 | 多重度 | 根拠・備考 |
|---|---|---|
| 注文 : 明細行 | 1 : N | 現行帳票は8行上限 → **v2 は無制限**（帳票側の改ページは Phase 6 の責務） |
| 注文 : 入荷 | 1 : N | **分納あり（頻度は稀）**。UIは1入荷・全量を標準経路に最適化 |
| 入荷明細 : 検収 | 数量会計 | **一部検収・返品あり**。合格数量／不合格数量／返品数量で持つ。返品分は注文残数量に復元 |
| 注文 : 請求 | 1 : N | 分割請求を許容（分納に随伴） |
| 注文 : 支払 | 1 : N | 分割支払いを許容 |

### 2.3 三方照合（PO・検収・請求）

- 明細行単位で「発注数量 vs Σ検収合格数量 vs Σ請求数量」＋単価・金額の突合。
- **許容差の規程は存在しない → 完全一致照合**。不一致（数量差・単価差・過納・過請求）はすべて**保留状態**を持ち、解消（修正 or 承認）まで支払いに進めない。
- 許容差はパラメータとして実装に残すが**初期値 0**（将来規程化された場合に「金額±X円」等の設定変更のみで対応）。
- **UI考慮**: 照合結果の状態表示は、将来の許容差導入を見込んで「**完全一致**」と「**許容差内一致**（Warning 寄りだが自動承認）」を視覚的に区別できる設計を最初から持つ（§3.4）。初期値0の間は後者が出現しないだけで、表示体系は先に定義しておく。

### 2.4 採番規程

- 形式: `{部署レター}{YYMMDD}-{連番3桁}`（例: `S260720-001`）。部署レターは部署ごとに規定。連番は**日次リセット（JST 基準）**、日あたり上限 999 件（実運用上十分）。金額の通貨は **JPY 固定**（多通貨対応はスコープ外）。
- **番号の不変性・非再利用を保証**する（厳密な無欠番は目標にしない）:
  - 採番は注文レコード作成と同一 DB トランザクション内で行う（`(テナント, 部署レター, 日付)` スコープの unique 制約＋競合時リトライ）。正常系では自然に連続する。
  - 発行後キャンセル（§2.1 の境界内）は番号を削除・再利用せず `cancelled` 状態で残す（5年保存・監査証跡と整合。「説明できない欠番」を作らない）。
  - 障害由来の稀な欠番は許容（無欠番保証は採番の直列化を要求し可用性コストに見合わない）。
  - ※着手時確認: 社内規程・経理運用に欠番禁止ルールがないこと（あれば本節を再設計）。

### 2.5 証憑・原本ファイル保存

- 見積書と本注文書は5年保存（法定証憑）。本注文書は発行後**不変・改ざん防止**が要件。
- **原本ファイル保存基盤（新規要件）**: 現行は「アップロード→抽出→削除」で**原本がどこにも残らない**。見積書PDF・図面・請書スキャン等の受領原本と、発行した注文書PDF（全版）を、**テナント分離されたオブジェクトストレージ**に案件・版と紐付けて保存する。要件: 追記専用（発行済み・受領済みファイルの上書き禁止）、ハッシュによる完全性検証、案件からの検索性、5年保存のライフサイクル管理。Phase 5 で保存基盤を導入し、Phase 6 の証憑出力・電帳法対応はこの基盤の上に載せる。
- 電帳法の射程・要件（真実性・可視性）は **Phase 6 着手時に一次情報で確認**してから断定する。

### 2.6 法令要件（取適法：中小受託取引適正化法）

買い手（発注側）ツールである以上、取適法（旧下請法、2026-01 施行の改正）の発注側義務をシステム要件として扱う。
※各要件の正確な射程・文言は**実装着手時に一次情報（公取委・中企庁の公式資料）で確認**してから断定する。

- **3条書面（発注書面）の記載事項充足**: 業務スキーマの必須項目が法定記載事項を網羅していることを v2 設計時にチェックリストで照合する（現行帳票は社内規格で対応済みの前提だが、システム発行に移行しても欠落しない構造にする）。
- **電子交付の承諾**: 発注書面を電子データで交付する場合は**相手方の事前承諾が前提**。取引先マスタに承諾フラグ（`accepts_digital`）を持ち、未承諾の取引先には電子交付経路を提供しない（PDF印刷交付のみ）。※メール自動送信はスコープ外のままだが、**手動のメール添付交付でも承諾管理は必要**なためフラグ自体は Phase 5 で導入する。
- **支払期日（60日ルール）**: 支払期日は受領日から起算して法定期間内。受領（検収）登録時に支払期日を自動算定・固定し、期日接近・超過をダッシュボードで警告する（§3.4）。三方照合の保留で支払いが止まる場合も**法定期日は延びない**ことを警告に反映する。
- **支払条件マスタ（自動算定の前提）**: 期日の自動算定ルール（締め日・支払サイト。例: 月末締め翌月X日払い）を**テナント既定＋取引先別上書き**のマスタとして持つ。60日ルールの上限チェックはこのマスタ値に対して行い、法定期間を超えるルールは登録時に拒否する。現行運用の「請求書は毎月X日必着」等もここに規定。

### 2.7 セキュリティ要件（アクセス制御）

- **権限マトリクス（ロール × リソース × 操作）を要件定義の正式成果物**とし、Phase 5 詳細設計の冒頭で作成する。実装の認可テストはこの表を正とする。
- **オブジェクトレベル認可（IDOR 対策）**: 注文番号は推測可能な連番であり、URL・IDを知っていることは認可根拠にならない。全リソースアクセスで tenant_id / department_id / 所有者を検証する。
- **トラスト境界の定義**: Cloudflare Access（入口）と Auth0（アプリ内）併存期は二層のトラスト境界を明文化し、片方が破られた場合の防御残存を設計時に評価する。
- **職務分掌の統制**: 「同一ユーザーが起案と最終承認を兼ねられない」制約をテナント設定で有効化可能とする（自社の単一ユーザー運用では無効）。
- 詳細な脅威分析は §基本設計 2.6 および `docs/security/THREAT_MODEL.md`（Phase 5 着手時に作成）。

## 3. 機能要件（テーマ別）

### 3.1 抽出スキーマ v2（現行帳票との差分。§基本設計 2.1 の2層分離が前提）

現行 `orderSchema`（v1）からの主な変更:

| 区分 | 項目 | v1 | v2 |
|---|---|---|---|
| 明細 | **図番** | なし | **追加**。図面チャネル（`drawingSchema.drawingNo`）との突合キー |
| 明細 | 行数 | 実質8行（帳票上限） | スキーマ上は無制限 |
| 明細 | 単価 | number 強制 | `number \| null`（協議中）＋単価未定理由 |
| ヘッダ | 発行日 | なし | 追加 |
| ヘッダ | 見積書受領日 | なし | 追加（仮→本の遷移イベント） |
| ヘッダ | 原材料支給の有無 | なし | enum（なし／有償／無償）＋有償時別紙明細（品名・引渡日・数量・単価・合計・決済期日/方法） |
| 発行側 | 発注部署／発注者／連絡先／受渡担当者／承認者 | なし | 業務データ側に追加（**AI抽出対象外**） |
| 状態 | 注文請書 | なし | 「請書受領」状態＋請書記載の確定納期 |

- **複数図面混在PDF（業務要件）**: 実務では「1PDF＝1図面」と「1つのPDF内に複数図面（複数ページ）」が混在する。1回のアップロードから**複数の抽出結果（ExtractionResult）が生成され、複数の明細行（OrderLine）にマッピングされる1対多**をデータフロー・UIの前提とする（パイプライン設計は §3.2、UI・データ設計への反映は Phase 5）。

### 3.2 AIパイプライン最適化

- 前提: **golden set + 評価ハーネスを先に整備**（正は**墨消し済みの元図面PDF**・初期10件。詳細は基本設計 §3「Phase 4a 詳細計画」。回帰検知と before-after 測定には十分、追加は「ハーネスで落ちた実例」優先で層別に拡充）。
- **前処理の第一目的はデータ最小化**（精度ではない）。図面本体（寸法・形状＝自社および取引先の技術情報）を外部 AI に送信せず、抽出に必要な領域（表題欄＋数量記載部）のみを送る。精度はその制約下での最適化課題であり、**精度を理由に最小化要件を緩めない**。
- **現行の crop-title-block は上記を達成していない（2026-08-29 判明）**: `setCropBox` / `setMediaBox` は表示領域の指定であり、`copyPages` で複製されたコンテンツストリームは無傷のまま Gemini File API へ送信されている。詳細と是正方針は基本設計 §3「Phase 4a 詳細計画」。
- 図面PDFはテキスト層なし（実測）→ VLM前提。OCR×VLMハイブリッド検討時も OCR 入力はラスタライズ経由。
- **ページ分割前処理（Split）**: マルチページPDFをそのまま VLM に投げず、**前処理として pdf-lib 等で1ページ1ファイルに分割し、各ページを独立したジョブとして抽出**にかける。精度低下と抽出漏れ（後半ページの無視）を防ぐため。分割は既存パイプライン（upload/classify/extract/validate）の upload と classify の間のステージとして追加する。
  - **エンドポイント契約の申し送り（#295）**: `crop-title-block` は `getAll('file')` で複数受け取る形をしているが、呼び出し元は 1 リクエスト＝1 ファイルで送信し `croppedFiles[0]` のみを読む**実質的な単一ファイル契約**。#295 で「検証失敗時は部分成功にせず全体拒否」に統一した（Copilot レビューの部分成功維持案は silent partial loss を温存するため REJECT）。複数入力の正式な契約（1アップロード→N結果）は本 split 実装時に定義する。
- **リソース枯渇（DoS）対策のハードリミット**: マジックバイト検証（PR-06 済）に加え、細工PDF・ページ数爆弾に対し (a) **ファイルサイズ上限 25MB（決定。現行実装値を維持）**、(b) **ページ数上限（例: 50ページ）**、(c) **パース処理・AI推論のタイムアウト上限** をハードリミットとして実装し、超過は即座に Reject（4xx）する。ページ数・タイムアウトの確定値は実装時に決定。
  - **上流制約（2026-08 判明 / #295 のスモークで発覚）→ 解消済み（#301 / 2026-08-22）**: `proxy.ts` を使う本アプリでは、Next.js がリクエストボディをメモリにバッファし、その上限は `experimental.proxyClientMaxBodySize`（既定 **10MB**）。超過分は**サイレントに切り詰められ、リクエスト自体は失敗しない**（公式ドキュメント記載の仕様）。結果として 10MB 超のアップロードは multipart が破損して `request.formData()` が throw し、`validateUploadFile` の 413 に到達する前に 500 となっていた。A1/A2 図面PDFは 10MB 超が珍しくないため**正当な入力が汎用 500 になる実バグ**であり、`crop-title-block` / `check-document-type` / `extract-drawing` の全アップロード系ルートに共通していた。
    - **採用した対策（3層）**: `proxyClientMaxBodySize: '32mb'`（バッファ上限。切り詰めが実質起きない位置に置く）＋ `MAX_REQUEST_BYTES = 26MB`（`request.formData()` より前に `Content-Length` で早期 413。`lib/ai/pipeline/upload.ts`）＋ 既存の `MAX_UPLOAD_BYTES = 25MB`（ファイル単体の業務上限 → 413）。**上限を何MBにしても「超過→切り詰め→multipart 破損→汎用 500」の崖は移動するだけで消えない**ため、パース前に落とす層を必須とした。ローカルスモークで 5/12/24MB→200、25.5/30MB→413、壊れた multipart→400 を実測。
    - **experimental の採用判断**: 公式は production 非推奨と明記するが、このバッファリングは `proxy.ts` を使う時点で既定 10MB が**すでに有効**であり、本設定は値を変えるだけで experimental な面積を増やさない。撤去・改名リスクは非 experimental なアプリ層ガード（`checkRequestBodySize`）が受ける。
    - **残存する弱点**: `Content-Length` が経路上で失われるとガードは不発になり、`readFormData` の 400 が唯一の受け皿になる（`checkRequestBodySize` は判定不能を warn ログに残す）。また `replicas: 1` / memory limit 1Gi に対し 25MB アップロード1本で proxy バッファ＋`File`＋`Buffer` の3コピー ≈ 75〜100MB を消費するため、**同時実行制御は Phase 4b の DoS ハードリミットへ申し送り**（本節 (b)(c) と同時に設計する）。
    - **Phase 5 / Auth0 移行時の設計材料（重要）**: このボディバッファは `proxy.ts` の matcher が `/api/:path*` を含むことの副作用であり、**認証をルート横断のミドルウェアから Data Access Layer（および Route Handler 内）へ移せば、バッファ自体が発生しなくなる**可能性が高い。Next.js 公式も、セキュリティチェックの大半はデータにアクセスする場所（DAL）で行うべきで、middleware を唯一の防御線にしてはならないとしており、本 repo の方針11「境界の構造的強制」とも同じ方向を向く。Auth0 移行（ADR-2）で認証の置き場所を動かす際は、①`proxyClientMaxBodySize` を撤去できるか、②`checkRequestBodySize` は残すか（fail-closed の本線防御としては残す想定）、を設計判断として明示的に扱う。matcher から外したルートで実際にバッファが発生しないことは、着手時に一次情報と実測で確認する。
  - **切り詰めのデータ整合性リスク**: 切り詰められたボディが偶然パースできた場合、破損PDFが「処理失敗」として握り潰される経路があり得る（§2.7 / 方針「抽出データと業務データの分離」に抵触）。上記 fix ではサイズ超過を**明示的な 413** に落とすこと。
- **非同期ジョブ実行（決定）**: アップロード完了後の解析は HTTP リクエストのライフサイクルから切り離し、**ブラウザのページを閉じても処理が継続する**サーバーサイドのジョブとして実行する。ユーザーは後から結果に戻れる（ジョブステータスの永続化＋一覧表示＋完了時のアプリ内通知）。設計は §基本設計 3。
- 施策候補（すべて測定とセット）: モデルカスケード（低信頼フィールドのみ上位モデル再抽出）／フィールド単位ルーティング／critic パス／OCR×VLM ハイブリッド（bbox 根拠付き）。
- 期限制約: `gemini-2.5-*` shutdown **2026-10-16**。3.x 移行 chore はハーネス整備直後に実施。**スタンス: 現行システム自体が完成形ではないため、精度低下リスクを過度に警戒したり厳密な合格基準を設けたりしない。ハーネスで before-after を測定・記録しつつ、期限に向けて淡々と移行する**（測定結果は Phase 4c の施策検討の入力として使う）。
  - **移行対象と期限（2つある）**: 現行モデルは `classify`=`gemini-2.5-flash-lite` / `extractOrder`=`gemini-2.5-flash` / `extractDrawing`=`gemini-3.1-flash-lite`（2026-09-05 に実コードで確認）。
    - **2026-10-16**: 2.5 系の `classify` と `extractOrder`。本 chore の必須対象。
    - **2027-05-07**: `gemini-3.1-flash-lite` の shutdown（Gemini deprecations ページで公表済み。推奨移行先は `gemini-3.5-flash-lite`）。`extractDrawing` も**任意の更新ではなく期限のある必須更新**であり、期限が後ろにあるだけ。本 chore に相乗りさせるか別 chore に分けるかは着手時に判断する。
  - **モデル選定方針**: **移行時点での最新モデルを採る。ただし具体的なモデル ID は本書に書かず `lib/ai/models.ts` を正とする**。Flash 系は 3.5 → 3.6 → 3.7（2026-08-13）→ 3.8（2026-09-03 GA）と6週間で3世代動いており、計画書に ID を固定すると即座に陳腐化するため。本書には用途と系列の対応だけを残す。
    - `classify` / `extractOrder` / `extractDrawing` はいずれも分類・構造化抽出・文書理解であり、Google が Flash-Lite 系に割り当てている用途に一致する。**既定は Flash-Lite 系の最新**とし、精度が足りない場合のみ Flash 系の最新を候補に上げてハーネスで比較する。
    - 2026-09-05 時点の最新は Flash-Lite 系が `gemini-3.5-flash-lite`、Flash 系が `gemini-3.8-flash`（一次情報: ai.google.dev / DeepMind モデルカード）。**着手時に必ず再確認する**。
  - **移行の実装コストは小さい**: `generateStructured`（`lib/ai/generate.ts`）は `temperature` / `top_p` / `top_k` / `thinking_budget` を設定せず、単一の user ターンのみを送る。Gemini 3 系の破壊的変更（サンプリングパラメータの無視・`thinking_budget`→`thinking_level`・末尾 Model ロール禁止）はいずれも該当しないため、実質はモデル ID の差し替えと測定になる。ただし 3.5 Flash-Lite は thinking の既定が `minimal` のため、`extractDrawing` を 3.1 Flash-Lite から移す際の品質差はハーネスで確認する。

### 3.4 フロント業務UI（Phase 5 と並走〜後）

- 現状の抽出フォームから、案件一覧・仮/本注文発行・進捗表示・検収／照合／支払まで扱う業務UIへ作り直し。**現行の独立した2画面（仮注文書作成＝図面解析／本注文書作成＝見積解析）は、「案件（注No）」を中心とする単一のフローに統合**する: 図面抽出も見積抽出も同一案件への入力チャネルであり、案件詳細画面から起案→承認→仮発行→見積取込→本発行→進捗と一貫して遷移する。ヘッダの設定・ユーザーアイコン（現状 404）の遷移先は、テナント設定（ワークフロー・支払条件マスタ）とユーザープロフィール（Auth0/AppUser）として Phase 5 の機能とともに実装する。
- API 出力契約は PR-05 で分離済みのため、バックエンドを巻き込まない。
- 高頻度ケース最適化: 標準経路は「1入荷・全量検収」を1アクションで完了。分納・一部検収はエスケープハッチとして提供。
- **ダッシュボード（案件一覧）**: 「自分の担当」「要対応（協議中／照合保留／支払期日切迫）」フィルタ。支払期日接近（例: 残15日）・超過のハイライト（§2.6 の60日ルール連動）。
- **My Tasks（自分ボール）ビュー＝必須要件**: 状態遷移の結果「現在、自分が処理すべき案件」（承認待ちで自分が承認者／差し戻しされた起案／照合保留の解消担当 等）が明確に一覧化されるビュー。ダッシュボードの最上位に置く。
- **取引先マスタ管理画面**: admin 限定。一覧・検索・登録・編集・論理削除（`is_active=false`）、電子交付承諾フラグの管理。
- **権限（RBAC・テナント/部署分離前提）**: role＝admin／user。一般ユーザーのデータアクセスは**自テナント・自部署**に分離。**admin は部署を跨いで案件の確認・操作が可能**。マスタ編集は admin のみ。注文の編集は作成者本人または admin。検収・支払確定操作を admin 限定にするかは Phase 5 詳細設計で決定（現状は実質単一ユーザーのため、モデルとして持ちつつ運用は緩く開始してよい）。
- **照合ステータス表示**: 「完全一致」「許容差内一致（Warning 寄り・自動承認）」「不一致（保留）」を視覚的に区別（§2.3）。
- **既知バグ（2026-08-22 / `fix/analyze-double-submit` 完了 #299）**: 仮注文書作成画面の「すべて解析」ボタンに実行中ガードが無く、連打すると `ADD_ITEMS` が同一 `id`（`CroppedFile.id` を流用）の明細行を重複 append する。React の duplicate key 警告（`AnalysisTable.tsx`）は症状にすぎず、実害は**明細行の同一性の崩壊**＝`UPDATE_ITEM` / `REMOVE_ITEM` が id 一致行を全件処理するため、重複行は常に同期更新され、1行だけ削除しようとすると両方消える。加えて Gemini API を件数分二重に呼び、チャンク単位のレート制御も無効化される。連打はトリガーの一つにすぎず、**投入済みファイルが `status: 'cropped'` のまま残る**ため解析完了後の再押下でも同じ重複が起きる。UI は Phase 5 後に作り直す前提だが、明細行は仮注文書の中身そのもの（§2.2）のため放置しない。対応は (a) 実行中の再入禁止（同期的な ref ガード ＋ ボタン disabled）、(b) 明細化済み `CroppedFile` の消費（`status: 'completed'` へ遷移させ再投入させない）、(c) **明細行 id を入力ファイル id から分離**（行ごとに `crypto.randomUUID()`）の3点。
  - **(c) を本 fix に含める判断（2026-08-22 決定）**: 当初は UI 作り直しへ繰り延べる方針だったが、(a)(b) が「重複行を作らせない」ガードであるのに対し (c) は「重複行が万一できても業務データが壊れない」構造的保証であり、変更が `use-drawing-analysis.ts` 内に閉じる（明細行と入力ファイルを id で突き合わせる箇所は他に存在しないことを実コードで確認）ため、繰り延べる理由がないと判断した。
  - 原則（実装済み・UI 作り直し後も維持する）: **明細行の id は行の identity であり、入力ファイルの id と同一視しない**（1入力→N明細になる split 実装後はなおさら成立しない。§3.2）。明細→入力ファイルの逆参照が必要になった時点で `OrderItem.sourceFileId` 等を追加する（現時点では読み手がいないため持たない）。
- **既知バグ（2026-08-22 / #301 のスモークで判明 → `fix/crop-error-state` で完了 #304 / 2026-08-23）**: `use-provisional-order.ts` の `processCrop` は catch 節で `{ progress: 100, status: 'cropped' }` を設定するため、**`/api/crop-title-block` が 400 / 413 / 415 / 500 のいずれを返しても UI 上は青い「クロップ済」バッジになる**。失敗が一切表示されない。#301 以前から存在するクライアント側の既存バグであり、#301 の回帰ではない。
  - **業務データは壊れない**: 解析への投入は `f.status === 'cropped' && f.base64` で絞られ、失敗ファイルは `base64` を持たないため解析に流れない（方針「抽出データと業務データの分離」は維持されている）。
  - **実害はカウントと導線**: `croppedCount` は `status === 'cropped'` のみで数えるため「すべて解析 (N件)」の N が失敗分だけ水増しされ、**全件失敗時はボタンが活性なのに押しても何も起きない**（`handleAnalyzeAll` が `croppedReadyFiles.length === 0` で即 return）。
  - **#301 の価値を打ち消している**: #301 で 25MB 超が正しく 413 を返すようになったが、この画面ではその 413 が「クロップ済」として握り潰されるため、サーバ側の改善がユーザーに届かない。エポック0 内での優先度は高い。
  - **実装（#304）**: 根本原因は `CropStatus` が `'error'` を持たず（`OrderItemStatus` は持つ＝非対称）、catch 節が「嘘の成功」以外を書けない構造だったこと。型に失敗を表現させたうえで、`CroppedFile` に `errorMessage` / `errorAction` を保持する。
  - **文言の写像は `code` 経由に決定（2026-08-23）**: HTTP ステータスを UI 文言へ直接写像するのではなく、応答本文の `code` を `resolveError` に渡して組み立てる（PR-08 で確立した「文字列マッチ廃止・code 分岐」の単一真実源に従う）。`code` を持たない応答（crop route の素の 400 / 500、`proxy.ts` の 401）のためだけに、HTTP ステータス由来の fallback（400→`ERR_VALIDATION` / 401→`ERR_UNAUTHORIZED` / 413→`ERR_FILE_TOO_LARGE` / 415→`ERR_UNSUPPORTED_MEDIA` / その他→`ERR_REQUEST_FAILED`）を `lib/api/drawing-api.ts` に置く。画面に出るのは `resolveError` の文言のみで、サーバ本文の生メッセージはログに留める。
  - **件数条件の統一**: `croppedCount` を解析側の絞り込み（`status === 'cropped' && base64`）と同一条件に揃えた。条件がずれていたことが「ボタンは活性なのに押しても何も起きない」の直接原因であり、**カウントと実処理の述語を分けない**ことを原則として維持する（UI 作り直し後も同様）。
  - **fetch 実装の一本化**: `use-provisional-order.ts` に重複していた fetch を `lib/api/drawing-api.ts` の `cropTitleBlock`（従来は呼び出し元ゼロのデッドコード）へ統合し、`AppError` を throw する実装にした。
- **Phase 4a からの申し送り（2026-09-17 / #340）**:
  - **解析失敗時のエラー文言を表示する**: `use-drawing-analysis.ts` の catch 節は明細の `notes` にエラー文言を書き込み `status: 'error'` とするが、`notes` はどこにも表示されないため、失敗理由が利用者に届いていない。UI 作り直しで表示する（格納先を業務項目の `notes` から分けるかは作り直し時に検討）。
  - **`surfaceTreatment` は AI 抽出を維持し、画面では非表示のままとする（決定）**: 当初は注文書に記載する想定だった項目の名残。現行の検証シート・明細表・コピー JSON には出ていないが、削除候補ではない。
  - **備考（`notes`）の手入力欄は現行 UI に存在しない**: #340 で AI 抽出の対象から外したため、明細の `notes` に値が入る経路は解析失敗時のエラー文言（前項）のみで、利用者が備考を入力する手段は無い。入力欄を設けるかは、前項の格納先の分離と併せて作り直し時に決める（エラー文言が `notes` に入ったまま入力欄を設けると、業務上の備考と失敗メッセージが同じ項目に混在するため）。

### 3.5 PDF証憑（Phase 6）

- Adobe PDF Services API で仮/本注文書を体裁付き帳票化。テンプレート（レイアウト）とデータを分離。
- 明細行数無制限に対応する改ページ／別紙明細（有償支給含む）。注文請書パートを含む。
- 5年保存を production 品質（不変・改ざん防止・検索性・監査ログ）で。電帳法は着手時に一次情報確認。

## 4. 非機能要件

`completed-form.md` §4 を品質バーとして適用する: 可用性・信頼性（フォールバック・再試行）／データ整合性（トランザクション境界・採番競合制御・抽出と確定の分離）／セキュリティ（Cloudflare Access + proxy 検証、秘匿情報の非ログ化、入力検証、最小権限）／可観測性（構造化ログ・メトリクス）／テスト（重要経路の自動テスト・AI評価ハーネス・CIゲート）／保守性（単一真実源・合成可能な設計）。

追加の非機能要件:

- **資源枯渇対策**: §3.2 のハードリミット（サイズ・ページ数・タイムアウト）に加え、認証済みユーザーに対しても API レート制限を課す（例: 採番・AI抽出エンドポイントの連打による日次連番の食い潰し・APIコスト暴騰の防止）。
- **監査証跡の一般化**: ApprovalLog（承認系）に限定せず、**発行・検収・赤黒・マスタ変更・権限変更**を含む重要操作すべてを「誰が・いつ・何を」の**追記専用 AuditLog** に記録する。ApprovalLog は AuditLog の一種（コメント付き承認イベント）として設計する。

## 1. ドメインモデル

 │                    請書受領(仮)/本発行/請書受領(本)/クローズ/キャンセル。§要件 2.1 と対応）

- **版管理**: Order は rev（版番号）を持ち、仮→本・変更注文を版遷移として一般化。発行済み版のスナップショット（SourceDocument の注文書PDF）は不変。

- **マルチテナント・部署分離（SaaS化前提）**: Order / OrderLine 以下の全業務データ・Vendor・AppUser 等の主要テーブルは **`tenant_id` を必須で持ち**、テナント内はさらに **`department_id`** でデータアクセスを分離する。すべてのクエリはテナント境界を強制するデータアクセス層を経由（RLS 等の実装手段は DB 選定後の Phase 5 詳細設計で決定）。admin の部署跨ぎアクセスは RBAC 層で許可する（テナント跨ぎは許可しない）。

- **進捗の導出**: 例）明細行の「検収済み」＝ Σ合格数量 ≧ 発注数量 − Σ返品数量。ヘッダの進捗表示は全明細行の集計。導出ロジックは単一モジュールに集約しテスト対象とする。
- **抽出データと業務データの分離**: AI抽出結果（信頼度・要確認付き生JSON）は `ExtractionResult` として別系統に保存し、人の確認を経て Order/OrderLine へ反映。誤抽出を業務記録に直接流さない。

## 2. データ設計方針

### 2.1 スキーマの2層分離（v2 の中核）

現行帳票の項目の大半は見積書・図面から抽出できない発行側情報であるため、単一真実源を2層に分ける:

- **extraction schemas**（`lib/ai/schemas.ts` 系譜）: 見積書・図面から AI が取れるものだけ。信頼度・要確認を持ちうる。
- **business schemas**（新設）: 発行・状態遷移に必要な全項目（§要件定義 3.1 の表）。DB列・PDF項目はこちらから派生。
- 両層の対応関係（どの抽出フィールドがどの業務フィールドの候補値になるか）をコード上で明示し、マッピングを1箇所に集約する。

### 2.2 採番の実装方針

`(部署レター, 日付)` ごとの連番テーブル（または unique index + リトライ）。注文レコード作成と同一トランザクション。詳細は Phase 5 の詳細設計で DB 選定後に確定。

### 2.3 状態機械

- 遷移は明示的な遷移関数のみ経由（任意の status 直接更新を禁止）。不正遷移は型＋実行時の双方で防ぐ。
- キャンセルは §2.1 の境界内でのみ許容し、番号・レコードを保持したまま終端状態へ。**境界を越えた後の取り消し・修正は赤黒処理**（マイナス数量の返品明細・相殺請求・相殺支払）で表現し、元レコードは不変のまま数量会計上で相殺する。赤黒明細は元明細への参照を持ち、監査上ペアで追跡できるようにする。

### 2.4 排他制御（楽観的ロック）

- 複数ユーザーが同一注文を同時処理（例: 検収の二重登録）した際のデータ競合を防ぐため、**Order および各明細系テーブル（OrderLine / ReceiptLine / Inspection 等）に `version`（または `updated_at`）カラムを持たせ、更新時に楽観的ロック**を行う。version 不一致は 409 相当で拒否し、UI は最新状態の再読込を促す。
- 採番（§2.2）のような一意性が必要な箇所は unique 制約＋トランザクションで担保し、楽観ロックは「更新の競合検知」に用途を限定する（悲観ロックは原則使わない）。

### 2.5 通知基盤（イベント駆動）

- 状態遷移を**ドメインイベント**として発行し、通知はイベント購読側で処理する（状態遷移関数に通知処理を直書きしない）。遷移して「自分のボール」になった瞬間に**アプリ内通知＋メール通知**を送れる構造を非機能要件として見込む（Webhook 等の外部連携もこのイベント基盤に接ぎ木する）。
- 通知失敗が状態遷移を巻き戻さないこと（遷移コミット後の非同期処理・リトライ）。
- ※このメール通知は**社内ユーザー向け**であり、スコープ外の「取引先へのメール自動送受信（注文書交付）」とは別物。メール送信基盤の選定（SES 等）は Phase 5 詳細設計で決定。

### 2.6 セキュリティ設計（認可アーキテクチャと脅威モデル）

**認可アーキテクチャ:**

- **実施点の一元化**: 認可判定を各 API ルートに散在させず、データアクセス層で tenant 境界を構造的に強制する（tenant_id なしのクエリを型レベルで組めなくする、または DB の RLS。手段は DB 選定後に確定）。「書き忘れたら漏れる」ではなく「書き忘れられない」構造を必須とする。
- **テナント分離の CI テスト**: 別テナント・別部署のリソースへのアクセスが全エンドポイントで 403/404 になることを自動テスト化し、CI ゲートに含める。マルチテナント最大の脅威（分離の破れ）を回帰テストで常時監視する。

**脅威モデル**（詳細は `docs/security/THREAT_MODEL.md` を Phase 5 着手時に作成し、living document として STRIDE で展開。以下は現時点の主要脅威と対策方針）:

| # | 脅威 | 対策方針 |
|---|---|---|
| 1 | **取引先マスタ改ざん→支払詐欺**（メール・将来の振込先の書き換え。BEC/内部不正の典型標的） | マスタ変更は admin 限定＋**変更の AuditLog＋変更時通知** |
| 2 | **アップロード文書経由のプロンプトインジェクション**（見積書・図面に指示文を埋め込み抽出値を操作） | LLM を信頼境界の内側に置かない。**抽出データと確定データの分離＋人の確認**を本脅威への明示的対策として位置づける |
| 3 | テナント分離の破れ | 認可一元化＋分離 CI テスト（上記） |
| 4 | 証憑の改ざん（Tampering。法定要件に直結） | SourceDocument の追記専用＋ハッシュ検証（Phase 6 設計入力） |
| 5 | 権限昇格・内部不正 | 職務分掌統制（起案・最終承認の兼務禁止設定）＋ AuditLog による検知 |
| 6 | ファイルアップロード攻撃面（細工PDF・ページ数爆弾） | マジックバイト検証＋サイズ・ページ数・タイムアウトのハードリミット（§要件 3.2） |
| 7 | 資源枯渇（採番連打・AI API コスト暴騰） | 認証済みユーザーにもレート制限（§要件 4） |

## 3. AIパイプライン設計方針

1. **ハーネス先行**: golden set（初期10件＋正解ラベルJSON）に対し per-field accuracy を算出する評価スクリプトを最初に作る。実行は手動トリガ（AI 呼び出しは CI に載せない）。詳細は下記「Phase 4a 詳細計画」。
2. 施策（カスケード等）は「精度↑ or コスト↓を数値で示せたら採用」。示せなければ入れない。
3. パイプラインは PR-06 で導入済みのステージ構造（upload/classify/extract/validate）に接ぎ木する。**split（ページ分割）ステージを upload と classify の間に追加**し、以降のステージはページ単位のジョブとして実行する（1対多の抽出結果）。ハードリミット（サイズ・ページ数・タイムアウト）は split 以前で検証し早期 Reject。
4. **非同期ジョブ実行基盤**: 「アップロード受付（同期・軽量: 検証＋原本保存＋ジョブ登録）」と「解析実行（非同期ワーカー）」を分離する。
   - ジョブ（状態: queued/running/succeeded/failed）と結果（ExtractionResult）を永続化し、UI はポーリング or 通知（§2.5 のイベント基盤）で再接続する。接続断・ページ閉鎖はジョブに影響しない。
   - ワーカーはページ単位ジョブを並列実行。**リトライは冪等**（同一ページの再実行が二重の ExtractionResult を作らない）に設計し、AI API の一時障害は指数バックオフで再試行、恒久失敗は failed としてユーザーに通知する。
   - 実行基盤の実装手段（Cloud Run + Cloud Tasks / キュー選定 等）は **ADR-1 と結合**して決定。ジョブ・結果の永続化が前提のため、**完全な非同期化は Phase 5（DB 導入）に載せる**。Phase 4b の split 実装時は同期実行のままでよく、ステージ構造だけ非同期化を見越して切っておく。

### Phase 4a 詳細計画（feat/eval-harness。2026-08-29 決定）

**golden set**

- 正は「**Adobe Acrobat Pro で図面本体を墨消しした元図面 PDF**」（クロップ済み画像ではない）。クロップ工程自体を評価対象に含めるため、入力はクロップ前の姿で保持する。
  - マスクは黒塗り注釈ではなく**墨消し（Redact）を適用しコンテンツ自体を削除**する（golden repo・Gemini File API へ持ち出す前提の被害低減）。
  - **残す領域**: 表題欄（図番・品名・材質・表面処理・備考）と**数量の記載部（粗さ記号の直上の数字。表題欄外にある）**。用紙サイズ・ページ構造は原本のまま維持する（`detectPageSize` と座標系を変えないため）。
- 置き場所: private repo `chumon-hub-golden`（PDF＋正解ラベル JSON を同居。正解ラベル自体も機密）。ハーネスは環境変数 `GOLDEN_SET_DIR` でローカル clone を参照する。本体 repo にはラベルの zod スキーマ・README・合成ダミー1件のみ置く。
- 結果 JSON に golden repo のコミットハッシュを記録し、モデル×ラベル版の組で測定を再現可能にする。
- **golden set は C-2（補集合マスク）の proxy でもある**: 「表題欄＋数量記載部を残し他を削除」という形は C-2 と実質同一。ラスタライザ導入前に C-2 の当たりを付けられる（差異はベクタ品質 vs ラスタのみ）。

**測定設計**

- 入力段を差し替え可能にし、同一 golden set・同一メトリクスで最小化方式を比較する。判断基準は「**真の最小化を満たしたうえで精度が保てるか**」であり、精度単独の優劣ではない。

| 記号 | 方式 | 真の最小化 | 位置づけ |
|---|---|---|---|
| A | 現行 crop-title-block 経由 | **×** | 現状ベースライン（最小化は効いていない） |
| C-2′ | 墨消し済み golden をそのまま投げる | ○ | **ラスタライザ不要。Phase 4a で即測定可能**。C-2 の proxy |
| C-1 | ラスタライズ→クロップ | ○ | 領域外のピクセルが存在しない。非連続な複数領域は別画像 or 合成 |
| C-2 | ラスタライズ→補集合マスク | ○ | 全体レイアウトが残り「右下の表題欄」という文脈を VLM に与えられる。複数領域を1画像で保持 |

- **測定順序**: まず **A と C-2′** を測る。差が小さければ C 系の実装へ素直に進む。差が大きい場合のみ C-1 / C-2 の作り込みに踏み込む（投資効率）。**2026-09-13 追記**: 10件では差が小さかったが、18件（A1・ラスタ出力 CAD を含む）では差が大きく、C-1 を第一候補に確定した（§3「Phase 4a 詳細計画」12.）。
- **「最小化なし」の上限値は測定しない**: マスクしていない原本を投げれば図面本体が外部送信されるため、測定目的であっても実施しない。上限値は諦め、A / C-1 / C-2 の相対比較で判断する。
- **fail-safe 原則（方式選択の制約）**: 「残す領域の指定」の失敗は情報欠落→精度低下として可視化されるが、「隠す領域の指定」の失敗は図面データが無言で送信される。したがってマスク方式を採る場合も必ず**「表題欄＋数量記載部を残し、それ以外を全て塗る」補集合として実装**し、検出漏れが黒く塗られる側に倒れるようにする。
- **ベクタのままのマスクは採用不可**: pdf-lib で黒塗り矩形を描画してもコンテンツストリームは無傷で、CropBox と同じ欠陥を再現する。マスクは必ずラスタライズ後に行う。真の墨消し（MuPDF 系のコンテンツ削除）はベクタ品質を維持できるが、別ランタイム/ネイティブバイナリの持ち込みを伴うため採用前に一次情報で確認する。
- **ラスタライザの依存追加**: 現状 `pdfjs-dist` / `sharp` / canvas 系はいずれも未導入で、方針8（依存を増やさない）と衝突するが、**データ保護要件を優先**する。Phase 4a では**測定用スクリプトに限定して導入**し、本番パイプラインへの投入は測定結果を見てから判断する。
- **領域検出は AI に依存できない**: 検出のために全体像を VLM へ送れば最小化の目的が消える。検出はローカル完結（罫線・矩形検出等）である必要がある。数量が表題欄外（粗さ記号の直上）にあるため最低2領域を扱う。現行の用紙サイズ別ハードコード座標はこの制約下では妥当な出発点であり、安易に廃止しない（テナント依存の外部化は §5 の未決事項）。
- 判定は2層: ①機械的正規化（NFKC・trim・連続空白統一・ハイフン類統一・空文字/undefined 同一視。フィールド別に大文字化・空白除去・ひらがな→カタカナ統一）②ラベル側許容リスト（`accepted` 配列）。同義語辞書は先回りで作らず、落ちた実例から `accepted` に育てる。
- 集計は match / mismatch / **both-empty** の3値（空欄一致による accuracy 水増しの可視化）。per-field accuracy＋全フィールド一致率。
- 出力: 実行ごとに model ID・日時・golden コミットハッシュ・**未コミット状態（`appDirty` / `goldenDirty`）**・per-case per-field 内訳を JSON 保存（`chore/gemini-3x` の before-after 材料）。

**テスト基盤**

      - **基準箱を表示箱（CropBox ∩ MediaBox）へ統一する（issue #343。#342 の CodeRabbit 指摘由来）**。`cropTitleBlockPdf` は MediaBox 基準、`rasterizeCropRegion` は pdfjs の viewport 由来で表示箱基準。表題欄は「表示されるシートの右下」にあり、ビューアが見せるのは CropBox のため、統一先は表示箱とする（MediaBox へ寄せる逆方向は採らない）。`cropTitleBlockPdf` はハーネスの A 段用として MediaBox 基準のまま残す。
      - `@napi-rs/canvas` は native prebuild を持つ依存であり ADR-4 の再検討トリガ③に該当する。本番投入時に musl 環境での起動スモークを行う。
    - **別 chore への申し送り**: ハーネスは1件ごとの進捗を出さないため、C-1 のように1件が重い段では無応答に見える。`caseId` の逐次出力を足す。

### エポック0 の申し送り（#297 / #299 / #301 / #304 由来）

- **リモートファイル寿命の設計（決定・実装済み）**: Google File API 上のファイルの寿命は `withUploadedFile` の `remoteCleanup: 'always' | 'on-error' | 'never'` で制御する。`check-document-type` は `'on-error'`（成功時は暗号トークンで `extract-order` へ寿命を手渡すため削除しない）。**「トークンの手渡しが起きなかった経路はすべて orphan になる」**のが本質で、handler の throw だけでなく **`isQuotation: false` 判定時も orphan** になっていた（2026-08-20 の残置ファイルとして実発生を確認）。後者は route 内で明示削除し、応答契約 `checkDocumentTypeResponseSchema` を `isQuotation` の判別可能ユニオンにして、参照先が存在しない `fileId` を返さない構造にした。
- **残存する orphan（Phase 5 で解消）**: 判定成功後にユーザーがブラウザを閉じる等で `extract-order` が呼ばれないケース。トークン TTL 5分に対しファイルは48時間残る。リクエストのライフサイクルから切り離した寿命管理が要るため、**非同期ジョブ実行基盤（基本設計 §3）と同時に解消**する。
- **小さな後追い（どの fix に相乗りしてもよい）**: `app/api/extract-order/route.ts` の削除処理が独自実装のままで、(a) `deleteRemoteFile` と重複、(b) 生の error を `logger.error` に渡しており #297 のレビュー指摘（SDK の `ApiError.message` は API のエラー応答本文そのものでリソース名が混入しうる）が未適用。`deleteRemoteFile` への一元化で両方が解消する。
- **ログの原則**: リモート削除の失敗ログは固定文言＋`error.name`＋HTTPステータスに限定し、例外オブジェクトを渡さない。`error.name` だけでは 403 / 404 / 429 / ネットワーク障害を判別できず orphan の原因追跡ができないため、値域の限定された `status` は残す。
- **#299 由来: 明細行の個別リトライ導線が無い**: 解析へ投入した `CroppedFile` を消費済み（`status: 'completed'`）にしたため、error で終わった行を同じファイルから再解析する導線が存在しない（元々存在したのは全件再解析＝バグ本体）。error 行は明細テーブル上で手動修正できるため実害は小さいが、**個別リトライは UI 作り直し（§3.4）で設計する**。
- **#299 由来: 自動テスト基盤が無い**: 本リポジトリにテストランナーが無く、回帰は Dev Container スモークのみで担保している。`orderReducer`（`use-order-items.ts`）は純関数で最初のユニットテスト対象に適する。→ **Vitest 4 の導入で決定（2026-08-29。基本設計 §3「Phase 4a 詳細計画」）**。orderReducer のユニットテストは Phase 4a 後続の別 PR で対応する。
- **#301 由来: 本番経路での `Content-Length` 保持を観測する**: Cloudflare エッジ→origin が chunked になると早期ガードが不発になる。Pod ログに `Content-Length is missing` / `is not a valid size` が出ていないかを確認し、出ている場合は `readFormData` の 400 が唯一の受け皿になっている状態として別途対処を検討する（32MB 未満は正しく 413 に落ちるため致命ではない）。あわせて Cloudflare ゾーンの Maximum Upload Size を 25MB 未満に下げていないかを確認する（Free/Pro の既定 100MB なら律速しない）。
- **#301 由来: メモリと同時実行**: `replicas: 1` / memory limit 1Gi に対し、25MB アップロード1本で proxy バッファ＋`File`＋`Buffer` の3コピー ≈ 75〜100MB。バッファ上限を 32MB に留めたのはこのため。**同時実行制御を入れずに上限をさらに引き上げてはならない**。Phase 4b の DoS ハードリミット（ページ数・タイムアウト）と同時に設計する。
- **#301 由来: 認証の置き場所とボディバッファ（Phase 5 / Auth0）**: ボディバッファは `proxy.ts` の matcher に `/api/:path*` が含まれることの副作用。認証を DAL / Route Handler 側へ移せば `proxyClientMaxBodySize` 自体が不要になりうる。ADR-2（Auth0）着手時の設計材料として §3.2 に詳述。
- **#304 由来: HTTP エラー応答→`AppError` の変換が2箇所に分かれている**: crop 経路は `lib/api/drawing-api.ts` の `fallbackCodeForStatus` / `toAppError` で解消したが、本注文経路の `hooks/use-order-processing.ts` `handleApiResponse` は **fallback コードを呼び出し側が渡す設計**（`ERR_CLASSIFY` / `ERR_EXTRACT`）のため、`proxy.ts` が返す `code` なしの 401 を必ず誤写像する（Cloudflare Access のセッション切れが「リクエスト失敗」と案内される）。統合は **Phase 4b（`lib/ai/contracts.ts` の zod 化）** と同時に行う: `handleApiResponse` は「エラー応答→`AppError`」と「成功応答の zod 検証」の2つを担っており、**切り出すべきは前者のみ**。fix PR で本注文側の fallback の決まり方を変えるのは挙動変更にあたるため見送った。
- **#304 由来: 仮注文画面の入力バリデーションが無言**: `use-provisional-order.ts` の `handleFiles` は PDF 以外（`file.type` と拡張子の双方が一致しないもの）を `croppedFiles` に追加せず**無言で破棄**する。ユーザーには何も表示されないため「ファイルを選んだのに画面が変わらない」状態になる。`'error'` 状態は #304 で導入済みなので、弾いたファイルを error 行として出せば同じ枠組みで可視化できる。§3.4 の UI 作り直しに送らず単独 fix にする価値があるかは、実機での再現条件（特にモバイルのファイルピッカーが `type` を空で返すケース）を確認してから判断する。
